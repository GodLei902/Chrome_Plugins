# 社交评论清理器多平台插件化解耦合重构方案

## 1. 文档目的

本文档用于规划社交评论清理器从“Instagram 单平台内容脚本”重构为“平台插件 + 通用运行时”的实现方式。

本方案只定义目标架构、职责边界、接口、迁移步骤和验收标准，不改变当前运行行为。完成方案评审后，再按阶段提交代码，避免一次性重写导致现有 Instagram 删除流程失去安全保护。

## 2. 背景与重构目标

当前项目已经具备以下稳定能力：

- Chrome MV3 扩展启动、目标标签页管理和任务锁。
- 目标 URL 规范化、白名单、关键词和帖子作者保护。
- 当前已加载评论/回复的扫描、候选筛选和回复优先处理。
- 预览、开始、暂停、停止、操作节奏、全局限频和删除结果确认。
- 通过 DOM 和页面可见 UI 操作，不调用 Instagram 私有接口。

主要问题是平台差异和通用任务流程混在同一处。后续增加 TikTok、YouTube、Facebook 等平台时，如果继续复制 social-comment-cleaner.js，会造成：

1. 每个平台重复实现暂停、停止、限频、统计、候选队列和错误状态。
2. 平台选择器、语言文本和删除流程修改时容易影响通用调度。
3. Service Worker、配置页和内容脚本都直接假设 Instagram URL 和消息名。
4. 现有 DOM 逻辑难以在 Node 测试中隔离，平台页面升级时回归范围过大。

本次重构目标：

- 将所有平台相关能力收拢为 PlatformPlugin 方法。
- 保留一个不理解平台 DOM 的通用任务运行时。
- 让新增平台主要通过新增插件和注册信息完成，不复制核心状态机。
- 保持现有安全边界：预览不删除、一级评论不删除、白名单和作者保护优先、无法可靠定位时暂停。
- 让纯规则、调度、限频和数据契约可以独立单元测试。

## 3. 当前耦合评估

### 3.1 当前模块状态

| 模块 | 当前职责 | 耦合判断 | 重构建议 |
| --- | --- | --- | --- |
| src/content/social-comment-cleaner.js | 面板、DOM 发现、稳定性、解析、菜单、删除、任务循环 | 高 | 优先拆成运行时、平台解析器、平台动作和 UI |
| src/content/rules.js | 用户名、URL、关键词和候选选择 | 中低 | 保留通用规则，去除 Instagram 命名和 URL 假设 |
| src/content/comment-surface-stability.js | 快照签名和稳定性判断 | 低 | 保持纯函数，运行时通过插件取得快照 |
| src/shared/* | 节奏、退避、限频 | 低 | 保持平台无关，类名和配置字段改为通用名称 |
| src/background/service-worker.js | 标签页启动、锁、限频、调试器悬停 | 中 | 保留通用调度，平台 URL 解析移入插件注册中心 |
| src/options/* | 配置收集、校验、启动和控制 | 中 | 由插件注册信息提供平台选择和 URL 校验 |

### 3.2 主要耦合点

1. run 是一个共享可变对象，扫描、删除、等待和 UI 绘制都通过隐式读写它通信。
2. scan()、process() 和 remove() 同时包含业务流程、DOM 查询、页面动作和后台消息。
3. 多语言展开入口、更多菜单、删除按钮和确认弹窗正则直接定义在内容脚本中。
4. Instagram 的评论链接格式、父子关系判断、作者识别和 DOM 行边界直接写在通用流程附近。
5. service-worker.js 和 rules.js 各自实现了目标 URL 规范化，平台边界存在重复。
6. Manifest 的 matches、host permissions 和脚本加载顺序只有 Instagram 版本，插件没有独立注册入口。
7. 测试目前主要覆盖规则和节奏，尚未能把内容脚本的解析、菜单和运行状态作为独立对象测试。

## 4. 重构原则

### 4.1 核心与平台分离

通用核心只处理：

- 会话生命周期和状态机。
- 候选队列、统计、数量/时长限制。
- 节奏、限频、锁和可取消等待。
- 规则策略的通用部分。
- 面板状态模型和消息路由。

核心不得读取 Instagram 选择器、语言文本、评论链接格式或平台专属 URL。

平台插件只处理：

- URL、页面匹配和平台前置检查。
- 登录/权限/异常页面识别。
- 评论容器发现、分页/展开和稳定快照采集。
- 平台评论 DOM 到统一 CommentRecord 的映射。
- 目标节点定位、菜单打开、删除确认和删除结果验证。
- 平台本地化控件标签和能力差异。

### 4.2 插件返回数据，不直接控制核心状态

插件方法返回标准数据或明确的 ActionResult，不直接修改核心的 TaskSession，也不直接决定任务是否完成。核心根据返回值更新状态、统计和候选队列。

### 4.3 能力声明优先于平台判断

平台差异使用能力声明表达，例如是否支持回复、自动加载、删除确认和帖子作者校验。核心根据能力决定流程分支，不使用 if (platform === 'instagram') 作为长期扩展方式。

### 4.4 失败必须可分类

插件不得吞掉页面异常。返回 unsupported、not-ready、permission-denied、challenge、rate-limited、ambiguous、not-found 等标准错误，核心统一决定暂停、跳过或完成。

### 4.5 先兼容现有全局脚本，再考虑构建工具

当前项目使用 Manifest 脚本数组和 globalThis 暴露模块。第一阶段继续使用这种方式，减少构建链变化；接口稳定后再评估是否引入打包和按平台拆包。

## 6. 平台插件契约

### 6.1 插件对象

插件通过 globalThis.SocialCommentPlatformRegistry.register(plugin) 注册。核心只依赖以下契约：

~~~js
{
  id: 'instagram',
  displayName: 'Instagram',
  matches: ['https://www.instagram.com/*'],

  capabilities: {
    supportsReplies: true,
    supportsNestedReplies: true,
    supportsAutoLoad: false,
    supportsCommentDelete: true,
    requiresAuthorConfirmation: true,
    supportsPreview: true,
  },

  identity: { ... },
  preflight: { ... },
  surface: { ... },
  comments: { ... },
  actions: { ... },
  errors: { ... },
}
~~~

插件对象只暴露能力和方法，不暴露内部 DOM 选择器。选择器、正则和本地化词表只能存在插件目录内部。

### 6.2 identity：平台身份和目标地址

以下方法全部从当前 service-worker.js、rules.js 和内容脚本中提取到插件：

~~~js
identity.normalizeTargetUrl(value)
identity.isTargetUrl(value)
identity.matchesPage(location)
identity.getTargetContext(document, location)
identity.getCurrentAccount(document)
identity.getContentOwner(document, targetContext)
identity.compareAccounts(left, right)
~~~

返回的 TargetContext：

~~~js
{
  platformId: 'instagram',
  canonicalUrl: 'https://www.instagram.com/p/shortcode/',
  contentId: 'shortcode',
  contentType: 'post',
  host: 'www.instagram.com',
}
~~~

Service Worker 不再自行解析 /p/、/reel/ 或其他平台路径，只调用注册中心的 normalizeTargetUrl()。

### 6.3 preflight：登录、权限和页面前置检查

~~~js
preflight.detectLogin(document)
preflight.detectPageState(document)
preflight.checkTarget(context)
preflight.checkDeletePermission(document, context)
preflight.getRestrictionReason(document)
~~~

统一返回：

~~~js
{
  ok: true,
  state: 'ready',
  account: { id: 'opaque-id', username: 'optional-internal-value' },
  owner: { id: 'opaque-id' },
  canDelete: true,
  reason: '',
}
~~~

账号名称只用于当前页面的保护和权限判断，不进入通用持久化会话，也不显示在面板中。未知、未登录、挑战、验证、限流或作者身份无法确认时，正式删除必须停止，预览可以按平台能力继续。

### 6.4 surface：评论面和稳定性

~~~js
surface.findCommentSurface(document)
surface.findScrollableSurface(surfaceElement)
surface.observe(surfaceElement, observerCallbacks)
surface.disconnect(observerHandle)
surface.getMutationVersion(observerHandle)
surface.snapshot(surfaceElement)
surface.isVisible(node)
surface.getScrollState(scrollableElement)
~~~

snapshot() 返回平台无关结构，不返回供核心长期保存的 DOM 引用：

~~~js
{
  connected: true,
  surfaceId: 'opaque-runtime-id',
  commentIds: ['1', '2'],
  data: [...],
  mutationVersion: 12,
  signature: 'stable-signature',
}
~~~

稳定性判断、快照签名和连续采样仍放在 shared/comment-surface-stability.js 或 core/wait-coordinator.js，但“如何找到评论面”和“如何生成评论数据”属于插件。

### 6.5 loader：展开和批次加载

~~~js
loader.findExpansionControls(surfaceElement)
loader.expand(control, context)
loader.findLoadMoreControls(surfaceElement)
loader.loadNextBatch(surfaceElement, context)
loader.getProgress(surfaceElement)
loader.hasReachedEnd(surfaceElement, progress)
loader.cancel(context)
~~~

Instagram 的 replyExpander、hiddenCommentExpander、loadMoreExpander、多语言标签和点击后等待逻辑全部放入 instagram/labels.js 与 instagram/loader.js。核心只理解：本轮是否新增评论、是否仍可加载、是否到达平台声明的结束状态。

### 6.6 comments：评论数据解析

~~~js
comments.collect(surfaceElement, context)
comments.toRecord(commentElement, context)
comments.getId(record)
comments.getParentId(record)
comments.isReply(record)
comments.getAuthor(record)
comments.getText(record)
comments.getElement(record)
comments.buildThreads(records)
comments.getPostAuthor(context, surfaceElement)
comments.getReplyIds(threads)
~~~

统一 CommentRecord：

~~~js
{
  id: 'platform-comment-id',
  parentId: 'platform-parent-id-or-empty',
  kind: 'root' | 'reply',
  username: 'normalized-or-display-value',
  authorId: 'optional-opaque-id',
  text: 'plain-text-content',
  isPostAuthor: false,
  childCount: 0,
  hasUnloadedReplies: false,
  element: null,                 // 仅当前动作周期短暂使用
  platform: { ... },             // 插件私有数据，核心不得解释
}
~~~

Instagram 的评论链接 /c/<id>、ul 判断回复、评论行边界、用户名提取、文本过滤和父级推断全部属于插件解析器。核心只接收 CommentRecord 和线程树。

### 6.7 actions：页面动作和结果确认

~~~js
actions.resolveElement(record, context)
actions.ensureReplyVisible(record, context)
actions.revealMenu(element, context)
actions.getMenu(element, context)
actions.openMenu(element, context)
actions.findDeleteAction(menuContext, context)
actions.confirmDelete(deleteAction, context)
actions.verifyDeleted(record, context)
actions.getHoverPoint(element, context)
~~~

当前 locateCommentElement()、ensureReplyDom()、revealCommentMenu()、commentMenuFor()、visibleDeleteDialog()、deleteButtonInDialog() 和 waitForDeleted() 的平台部分全部迁移到这里。

核心新增通用流程：

~~~text
resolveElement
  -> ensureReplyVisible
  -> revealMenu
  -> getMenu/openMenu
  -> findDeleteAction
  -> core.wait(deleteDialogDelay)
  -> confirmDelete
  -> verifyDeleted
~~~

插件不负责更新删除计数。只有 verifyDeleted() 明确返回成功，核心才把候选加入 processedIds 并增加 deleted。

### 6.8 errors：平台异常分类

~~~js
errors.classify(error, context)
errors.toUserMessage(classifiedError)
errors.isRetryable(classifiedError)
~~~

Instagram 的 challenge_required、try again later、验证、限流、权限不足、菜单不明确和 DOM 不匹配判断放入 instagram/errors.js。核心只处理标准错误类别：

~~~text
not-ready       等待页面或评论区
not-found       目标节点/容器不存在
ambiguous       找到多个不确定元素，必须暂停
permission      没有删除权限或作者身份不明
challenge       验证、挑战、限流或风险提示
rate-limited    可等待的操作额度不足
unsupported     平台不支持该能力
cancelled       用户暂停或停止
unknown         未分类错误，默认暂停
~~~

## 7. 通用核心设计

### 7.1 CleanerRuntime

CleanerRuntime 取代当前内容脚本中的 scan()、process() 和部分 start()，只依赖插件契约：

~~~js
const runtime = createCleanerRuntime({
  platform,
  settings,
  transport,
  ui,
  clock,
  wait,
  pace,
});
~~~

核心流程：

~~~text
preflight
  -> acquireLock
  -> discoverStableSurface
  -> platform.loader.expand/load
  -> platform.comments.collect
  -> candidatePolicy.select
  -> preview 或 executeCandidates
  -> 删除后重新稳定和扫描
  -> 平台报告无更多数据时完成
~~~

核心不得调用 document.querySelector()，不得匹配平台文本，不得判断评论链接格式。

### 7.2 TaskSession

将当前 run 拆为显式对象，避免函数通过闭包互相写入：

~~~js
{
  id,
  mode: 'preview' | 'run',
  status: 'idle' | 'preflight' | 'scanning' | 'running' | 'cooling-down' | 'paused' | 'completed' | 'error',
  target,
  startedAt,
  stats: { scanned, loaded, matched, deleted, skipped },
  candidates,
  seenIds,
  matchedIds,
  skippedIds,
  processedIds,
  limits,
  pauseReason,
  lastError,
}
~~~

TaskSession 只提供 pause()、stop()、complete()、fail() 等状态变更方法，UI 通过 getSnapshot() 读取，不直接写入内部字段。

### 7.3 WaitCoordinator

统一封装以下当前散落的等待逻辑：

- 固定延迟。
- 条件轮询。
- Mutation 防抖。
- requestAnimationFrame 连续采样。
- 平台稳定快照。
- 暂停/停止时取消所有等待。

每次等待返回可取消 Promise，并绑定会话 AbortSignal。禁止继续使用单个共享 run.timer 覆盖多个并发等待。

### 7.4 CandidatePolicy

将通用筛选保留在核心：

~~~js
candidatePolicy.prepareRules(settings)
candidatePolicy.selectCandidates(threads, rules, platform.capabilities)
candidatePolicy.isWhitelisted(record, rules)
candidatePolicy.isAuthorComment(record, context)
candidatePolicy.matchesKeyword(record, rules)
~~~

平台插件只负责把页面数据转换为统一线程；一级评论、回复优先、白名单和关键词匹配不属于 Instagram 插件。

### 7.5 UI 与业务解耦

面板只接收 UiSnapshot：

~~~js
{
  platformName,
  targetLabel,
  status,
  waiting,
  error,
  stats,
  capabilities,
  actions: { canStart, canPreview, canPause, canStop },
}
~~~

按钮事件只调用核心命令：start、preview、pause、stop。面板不调用插件方法，不读取 DOM 评论，不判断删除菜单。

## 8. 后台与消息协议调整

### 8.1 Service Worker 通用化

service-worker.js 保留以下平台无关能力：

- 找到/创建/激活目标标签页。
- 等待页面完成加载。
- 目标任务锁、锁续租和释放。
- 所有平台共享或按平台隔离的限频额度。
- 调试器真实鼠标移动。

以下逻辑移出 Service Worker：

- Instagram /p/、/reel/ 解析。
- Instagram 页面是否为目标帖子判断。
- 评论菜单、删除按钮和页面状态识别。

锁键改为：

~~~text
socialCommentCleanerLock:<platformId>:<canonicalTargetUrl>
~~~

限频键建议改为：

~~~text
socialCommentCleanerRateLimit:<platformId>
~~~

### 8.2 消息名称

新增通用消息名：

~~~text
SC_LAUNCH
SC_START
SC_PREVIEW
SC_PAUSE
SC_STOP
SC_PING
SC_ACQUIRE_LOCK
SC_RELEASE_LOCK
SC_RENEW_LOCK
SC_RATE_ACQUIRE
SC_HOVER_POINT
SC_SAVE_SESSION
SC_GET_SESSION
SC_CLEAR_SESSION
~~~

迁移期间继续接受 ICC_* 消息并转换为 SC_*，待 Instagram 插件迁移完成且兼容周期结束后再删除旧别名。消息中显式携带 platformId 和 canonicalTargetUrl，不通过消息名推断平台。

### 8.3 悬停能力边界

真实鼠标移动是浏览器能力，不属于任何平台。插件通过 getHoverPoint(element) 返回坐标，核心发送 SC_HOVER_POINT，后台使用调试器完成移动。这样 TikTok 或其他平台可复用真实指针能力，同时各平台仍可自行决定悬停目标位置。

## 9. 配置与插件注册

### 9.1 统一配置结构

~~~js
{
  platformId: 'instagram',
  targetUrl: 'https://www.instagram.com/p/shortcode/',
  whitelist: '',
  deleteKeywords: '',
  sessionLimit: 'unlimited',
  sessionMaxMinutes: 120,
  pace: { ... },
  platformOptions: {
    autoLoad: false,
  },
}
~~~

节奏和通用限制保持平台无关；只有确实由平台能力决定的选项放在 platformOptions。新增平台不得复制整套设置字段。

### 9.2 设置页职责

设置页通过插件注册中心取得：

- 平台显示名。
- 目标 URL placeholder 和校验方法。
- 是否支持回复、自动加载、正式删除。
- 平台专属可选字段。

设置页只保存规范化后的配置，不保存 DOM 节点、菜单文本或账号名称。目标 URL 的规范化统一调用 platform.identity.normalizeTargetUrl()。

## 10. Manifest、权限和打包策略

### 10.1 第一阶段兼容策略

在没有构建工具前，Manifest 继续使用经典脚本数组，加载顺序调整为：

~~~text
shared 通用模块
core 契约、注册中心和运行时
platform/instagram 插件文件
content-entry.js
~~~

每个平台插件都必须在注册前检查当前页面是否匹配；不匹配时只注册元数据，不执行页面扫描。

### 10.2 后续平台接入

新增平台时同时增加：

1. 插件目录和注册项。
2. Manifest matches 与 host permissions。
3. 平台能力和选项默认值。
4. 平台插件单元测试和 DOM fixture。
5. README 的支持范围和权限说明。

不能为了支持新平台而把所有平台域名一次性加入权限；权限应随插件能力和发布版本明确增加。

### 10.3 构建优化时机

第一阶段不引入打包器。至少有两个平台插件、脚本数量影响加载性能或需要按平台拆包时，再在 scripts/package-extension.mjs 中增加构建清单校验和插件按平台打包。构建产物必须仍可通过 node --check、npm test 和 git diff --check 验证。

## 12. 分阶段实施计划

### 阶段 0：建立契约和回归基线

- 新增 platform/contract.js、platform/registry.js 和统一数据结构。
- 给当前 Instagram 实现增加适配层，但暂不改变消息名和行为。
- 补充当前工作区的静态检查、规则测试和安全边界测试。
- 验收：现有 npm test 通过，Preview 和现有运行链路代码路径不改变。

### 阶段 1：提取纯平台能力

- 提取 URL、标签、错误分类和评论记录转换。
- 提取 InstagramCommentRules 中与平台无关的候选策略。
- 让 rules.js 不再出现 Instagram 前缀。
- 验收：插件解析器可用固定 DOM fixture 测试，核心不读取 Instagram 文本。

### 阶段 2：提取评论面和解析器

- 将评论容器发现、评论行解析、线程构建和稳定快照迁移到 Instagram 插件。
- core/wait-coordinator.js 只接收插件快照和稳定性结果。
- 验收：容器替换、Mutation、虚拟列表、一级/回复映射测试通过。

### 阶段 3：提取页面动作

- 将回复展开、悬停、菜单、删除确认和删除结果验证迁移到 instagram/actions.js。
- 核心只执行统一删除模板，删除成功必须由插件返回明确结果。
- 验收：菜单不明确、删除项缺失、确认超时和节点重绘均进入正确暂停状态。

### 阶段 4：提取运行时和 UI

- 将 run 拆成 TaskSession。
- 将 scan/process/start/pause/stop 迁移到 CleanerRuntime。
- 面板改为订阅 UiSnapshot，不再直接读写业务状态。
- 验收：Preview、Start、Pause、Stop、Resume、限频、会话上限和锁续租行为与当前一致。

### 阶段 5：后台、设置页和消息协议通用化

- 引入 platformId，统一 URL 解析、锁键和消息名。
- 保留 ICC_* 兼容别名一个版本周期。
- 设置页从注册中心生成平台选项和 URL 校验。
- 验收：配置页、自动打开目标标签页、暂停/停止控制和 Service Worker 重启恢复均通过。

### 阶段 6：新增第二个平台试点

- 选择一个评论层级、删除入口和权限模型清晰的平台作为试点。
- 只实现该平台插件，不修改核心运行时流程。
- 记录插件契约中缺失的能力，优先扩展能力声明，不加入平台特判。
- 验收：第二个平台只新增插件目录、注册项、Manifest 权限和测试，不复制核心状态机。

## 13. 测试和验收标准

### 13.1 核心单元测试

- 会话状态转换、暂停/停止取消等待和重复启动保护。
- 候选队列去重、回复优先、一级评论保护、白名单和作者保护。
- 节奏状态机、限频、退避、会话删除数和最长运行时间。
- 插件异常到核心状态的映射。
- 任意插件不支持回复或删除时，核心不执行相应动作。

### 13.2 插件单元测试

- URL 规范化和页面匹配。
- 登录、作者和权限状态识别。
- 评论面发现、滚动/展开入口和稳定快照。
- 评论 ID、作者、文本、父子关系和 DOM 行定位。
- 多语言菜单、删除项和确认弹窗识别。
- 删除成功、删除失败、节点重绘和菜单歧义。

### 13.3 契约测试

每个插件都必须通过同一套契约测试：

~~~text
能否返回合法 platformId
能否规范化并反规范化目标 URL
不支持的能力是否返回 unsupported
所有动作是否可取消
异常是否包含标准 error.code
插件是否不直接修改核心 TaskSession
~~~

### 13.4 静态和浏览器验收

- node --check 覆盖所有插件、核心和后台脚本。
- npm test 覆盖纯模块和契约测试。
- git diff --check 无空白错误。
- 使用 Preview 和测试账号验证 Instagram 页面真实 DOM。
- 真实删除仍需小批量、可回滚的测试内容；静态测试不能证明平台删除成功。

## 14. 风险与取舍

### 14.1 不要把所有页面动作抽象成过度通用的选择器接口

平台 DOM 差异很大。核心只需要稳定的动作结果，不应定义“所有平台共用一个 CSS selector”。插件内部可以使用 ARIA、角色、文本和平台特有的多级回退策略。

### 14.2 不要把平台私有数据泄漏到核心

CommentRecord.platform 可以保留插件私有字段，但核心只能把它原样传回插件，不能读取 Instagram 专属字段。这样不会把 pk、内部接口字段或 React 节点结构固化到通用代码。

### 14.3 不要在第一阶段同时恢复自动分页

自动加载会同时改变扫描边界、虚拟列表和删除时序。先完成平台插件边界，再单独以插件能力实现 loader.loadNextBatch()，避免把分页问题和解耦合问题混在一次变更中。

### 14.4 保留兼容层，但设置删除期限

旧的 ICC_* 消息、InstagramComment* 全局名称和旧配置字段可以在迁移期间由兼容层转换。兼容层应记录目标删除版本，不能永久存在，否则会形成新的双重接口。

## 15. 完成定义

满足以下条件，才认为插件化解耦合完成：

1. core/ 中没有 Instagram URL、DOM 选择器、多语言评论文本或 Instagram 错误码。
2. service-worker.js 不再自行解析任何平台路径。
3. Instagram 的评论发现、解析、展开、菜单、删除和页面异常均由插件方法提供。
4. CleanerRuntime 可以在不修改代码的情况下加载另一个符合契约的插件。
5. 所有插件通过统一契约测试，核心测试不依赖真实 Instagram DOM。
6. Preview、Pause、Stop、锁、限频、节奏和安全保护在重构前后行为一致。
7. 新增第二个平台时，不复制核心运行时、候选策略、面板和节奏模块。
