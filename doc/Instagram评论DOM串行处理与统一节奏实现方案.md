# Instagram 评论 DOM 串行处理与统一节奏实现方案

## 1. 背景与决定

当前清理器会自动展开多个回复入口、扫描多个一级评论，并在候选队列中连续处理删除。评论分页、回复展开、评论菜单和删除动作的节奏彼此独立；其中评论菜单还依赖 `chrome.debugger` 发送真实鼠标移动来显示悬停控件。

本方案将运行方式调整为：

- 继续使用 Instagram 页面已有的可见 DOM 和页面 UI；不主动调用、重放或修改 Instagram 评论分页、读取或删除接口。
- Preview 与正式开始使用不同的展开策略。
- 正式开始时，以一个一级评论为一个完整处理单元：展开一个、扫描该评论的回复、处理完该评论下的候选、确认页面稳定后，才进入下一个一级评论。
- 展开、分页、打开菜单、删除和二次确认都接入同一个动作节奏协调器。
- 不再依赖 `chrome.debugger`、`Input.dispatchMouseEvent`、合成悬停事件或模拟鼠标移动。

本方案的目标是降低单次任务的页面动作密度、保持删除语义可验证，并让每一步在页面结构不明确时安全暂停。它不承诺能够规避或绕过 Instagram 的自动化识别、限流、验证或其他风控。

## 2. 范围与非目标

### 2.1 本次范围

1. 区分 Preview 和正式开始的回复展开与处理流程。
2. 正式开始改为按一级评论串行处理，不预先建立跨多个一级评论的大删除队列。
3. 将回复展开、一级评论分页、评论菜单、删除和二次确认纳入统一的随机休息与动作额度控制。
4. 移除调试器悬停路径，改为仅根据目标评论行内可定位的评论选项控件打开菜单。
5. 保留当前 DOM 分页、回复优先、白名单、帖子作者保护、暂停、停止、锁和删除结果验证。
6. 补齐相关单元测试、回归测试和真实浏览器验收记录要求。

### 2.2 非目标

- 不调用 Instagram 私有或未公开的 GraphQL、REST、删除或分页接口。
- 不包装、读取、重放或改写 `fetch`、`XMLHttpRequest` 及网络响应。
- 不模拟鼠标轨迹、键盘输入、触控行为或其他用户输入来隐藏自动化特征。
- 不在评论选项按钮不存在或用途不明确时猜测并点击其它按钮。
- 不把随机等待作为绕过平台风控的保证。
- 不删除一级评论；只在权限、作者、白名单和关键词规则均通过时处理已加载回复。

## 3. 关键概念

### 3.1 接口页、UI 渲染批次与处理单元

Instagram 页面内部一次请求可能返回约 50 条主评论，但评论区当前 DOM 可能只渲染约 10 条。这两者不能混为同一个“分页数量”。

| 概念 | 含义 | 本方案如何使用 |
| --- | --- | --- |
| 接口页 | Instagram 页面内部一次请求返回的数据量 | 只作诊断背景，不读取、不依赖、不按此数量处理 |
| UI 渲染批次 | 评论容器滚动或点击加载后，实际新增到 DOM 的评论 ID 集合 | 以新增 ID、加载状态和稳定快照判断是否完成一批 |
| 一级评论处理单元 | 一个一级评论及其当前可见、可展开的回复 | 正式开始模式的唯一串行工作单位 |

因此，DOM-only 方案仍需要页面自身滚动或点击“加载更多”来把后续评论带入 DOM。扩展不直接取得或消费页面内部 50 条接口数据。

### 3.2 处理单元状态

正式开始模式为每个一级评论建立短期状态；状态只保存 ID、统计、结果和原因，不保存 DOM 节点或菜单文本。

```js
{
  parentId: '...',
  status: 'pending',
  expanded: false,
  replyIds: [],
  candidateIds: [],
  processedIds: [],
  reason: ''
}
```

状态流转：

```text
pending
  -> expanding
  -> waiting-replies
  -> scanning
  -> deleting-replies
  -> settling
  -> completed
```

任何阶段出现验证、限流、权限不明确、菜单不唯一、删除结果不明确、DOM 被替换且无法重新定位等情况，都转入会话 `paused`，不得跳过后继续处理下一个一级评论。

## 4. 模式与流程

### 4.1 Preview 模式

Preview 的目的只是展示当前页面范围内的统计和候选。它可以按顺序展开当前 UI 批次中的多个一级评论，以获得较完整的统计，但每一次展开仍必须等待结果确认与页面稳定。

```text
确认页面与评论容器
  -> 获取当前 UI 批次的一级评论
  -> 选择下一个未展开一级评论
  -> 等待展开动作节奏
  -> 点击回复展开入口
  -> 等待新回复 ID 或回复容器出现并稳定
  -> 扫描并累计统计
  -> 重复直到当前批次已扫描
  -> 等待分页动作节奏
  -> 点击“加载更多”或滚动评论容器
  -> 等待新一级评论 ID 与稳定快照
  -> 重复或在有界完成条件下结束
```

Preview 绝不：

- 打开评论选项菜单；
- 查找或点击删除动作；
- 改变评论页面内容；
- 安排自动刷新续跑。

### 4.2 正式开始模式

正式开始采用“一级评论串行处理”。只要当前一级评论尚未完成，就不会展开、扫描或删除另一个一级评论的回复。

```text
确认目标、登录、内容作者和删除权限
  -> 获取当前 UI 批次的一级评论
  -> 选择第一个未完成一级评论
  -> 等待展开动作节奏
  -> 展开该一级评论的回复
  -> 等待数据与 DOM 稳定
  -> 仅扫描该一级评论下的回复
  -> 应用作者保护、白名单和关键词规则
  -> 逐条处理该一级评论下的候选回复
  -> 每条删除确认后等待页面稳定
  -> 标记该一级评论完成
  -> 选择下一个一级评论
  -> 当前 UI 批次完成后才加载下一批
  -> 连续无增长且达到完成条件后停止
```

正式开始不再采用以下旧路径：

```text
展开多个一级评论
  -> 扫描整页
  -> 建立跨多个一级评论的大候选队列
  -> 连续删除
```

## 5. 动作节奏与统一限频

### 5.1 统一动作类型

所有会改变页面状态或促使页面加载数据的动作均进入同一个协调器：

| 动作类型 | 说明 |
| --- | --- |
| `expand-replies` | 点击一个一级评论的回复/隐藏回复展开入口 |
| `load-more` | 点击当前评论面中的“加载更多评论或回复”入口 |
| `scroll-comment-surface` | 滚动真正的评论容器，以触发页面自身的懒加载 |
| `open-comment-menu` | 点击目标回复行内唯一的评论选项控件 |
| `delete-reply` | 点击当前新出现删除表面中的唯一删除动作 |
| `confirm-delete` | 在可验证的二次确认表面中点击唯一删除动作 |

每个动作固定经过：

```text
确认任务未暂停或停止
  -> 申请全局动作额度
  -> 生成内置随机休息时间
  -> 等待，且等待可被 Pause/Stop 取消
  -> 执行动作
  -> 等待该动作的可验证结果
```

动作额度、随机等待和结果确认属于运行安全控制；它们必须由核心的通用模块提供，Instagram 插件只负责动作本身和结果判定。

### 5.2 现有配置调整

当前“两次删除之间等待”“删除前等待”“批次间等待”和“连续删除后休息”分散在不同调用处。迁移后保留用户已配置的删除相关节奏含义，但内部改为按动作类型获取节奏。

建议：

1. `operation` 用作任一相邻页面动作之间的基础随机等待。
2. `deleteDialogDelay` 仅用作菜单打开后、点击删除动作前的额外等待。
3. `rest` 与 `maxConsecutive` 按已确认删除的回复数量触发，不将展开和分页计为删除数量。
4. `rateLimit` 记录全部动作，而不只记录删除。
5. 删除 `endProbePending` 导致分页动作跳过休息的特殊路径。

## 6. DOM 分页与稳定性

### 6.1 当前批次处理边界

1. 先发现并绑定当前评论容器。
2. 读取当前可见一级评论 ID，建立本批次顺序。
3. 完成当前批次所有一级评论处理后，才能触发下一次分页。
4. 分页后重新发现评论容器和一级评论；不得复用已被虚拟列表替换的 DOM 节点。

### 6.2 分页动作

页面存在可见且唯一的加载入口时，优先点击该入口；不存在时才滚动真正的评论滚动容器。不得滚动整个页面来代替评论面分页。

#### 6.2.1 容器选择与单批次加载位置

滚动前必须重新发现评论面及其可滚动容器。候选容器同时满足以下条件才可使用：

1. 容器连接在当前 `document`，可见，且 `overflow-y` 为 `auto`、`scroll` 或等效的可滚动值；
2. 容器可容纳当前评论面中的评论 ID，且 `scrollHeight > clientHeight`；
3. 不是 `document.body`、`document.documentElement` 或整页滚动根节点。

选定容器后，记录本次动作开始时的最大可滚动位置。当前已验证的页面需要到达该批次的容器底部才能触发懒加载，因此默认加载位置为 `initialMaxTop`，不预设固定像素的提前加载距离：

```js
const startTop = Number(scroller.scrollTop) || 0;
const initialMaxTop = Math.max(0, Number(scroller.scrollHeight) - Number(scroller.clientHeight));
const targetTop = Math.max(startTop, initialMaxTop);
```

这里的 `initialMaxTop` 只在动作开始时计算一次。滚动中如页面已经追加内容并使 `scrollHeight` 增长，本次动作仍停在原目标，不追逐新的底部；随后进入稳定等待、扫描和当前 UI 批次处理。下一批分页才重新计算目标。这样一次 `scroll-comment-surface` 只尝试触发一批数据，不会在一次动画内连续跨越多批评论。

如果开始位置已在加载位置，不人为先上滚再下滚制造抖动；直接按既有规则观察加载指示器、入口变化和新 ID。没有增长时记为一次有界的无增长探测，而不是把整页滚动作为兜底。

#### 6.2.2 分帧滚动与速度曲线

不得使用 `scrollTo({ behavior: 'auto' })` 瞬间跳到底部，也不直接使用浏览器 `behavior: 'smooth'`。后者的时长和缓动曲线由浏览器决定，无法统一取消、记录或在测试中验证。

实现使用 `requestAnimationFrame` 逐帧写入已确认评论容器的 `scrollTop`。总时长按本次距离和容器高度计算，并限制在合理范围：

```js
const distance = targetTop - startTop;
const speedPxPerSecond = clamp(scroller.clientHeight * 1.6, 420, 720);
const durationMs = clamp(distance / speedPxPerSecond * 1000, 360, 1400);
```

速度不能全程严格线性，也不能逐帧随机抖动。采用 18% 短加速、64% 近似匀速、18% 短减速的梯形速度曲线：中段速度固定，起止位置速度为零；其峰值约为平均速度的 1.22 倍，视觉连续且变化可预测。设归一化时间 `t` 为 `0` 至 `1`，`r = 0.18`，位置进度为：

```js
function progressAt(t, r = 0.18) {
  if (t <= r) return t * t / (2 * r * (1 - r));
  if (t >= 1 - r) return 1 - (1 - t) * (1 - t) / (2 * r * (1 - r));
  return (t - r / 2) / (1 - r);
}

scroller.scrollTop = startTop + distance * progressAt(elapsedMs / durationMs);
```

动作节奏协调器中的随机等待只发生在该次滚动前；单次滚动的帧间速度保持确定性，不以随机速度伪造用户输入。`scroll-comment-surface` 的额度按一次完整滚动动作计数，不按动画帧重复计数。

#### 6.2.3 完成、重绘与取消

每个动画帧都检查会话仍处于运行状态、目标容器仍连接且仍是当前评论面的滚动容器。Pause、Stop 或会话取消时立即取消下一帧；容器被页面重绘、断开或无法重新确认时停止向旧节点写入，重新发现评论容器并进入稳定判断。不得因容器替换而转为滚动整页。

滚动结束后记录实际 `scrollTop`、本次目标和初始 `scrollHeight`，再等待加载指示器、Mutation 防抖和稳定快照。只有新出现此前未见的一级评论 ID，或已知加载入口发生可确认变化时，才认为本次分页有效。页面 `window.scrollY` 在动作前后应保持不变；若发现整页发生滚动，正式模式暂停并记录容器定位异常。

一次分页成功至少需要满足：

1. 评论容器仍连接在当前页面；
2. 加载指示器已结束，或页面给出可确认的入口状态变化；
3. Mutation 防抖和稳定快照检查通过；
4. 新出现至少一个此前未见的一级评论 ID，或已知加载入口发生可确认变化；
5. 没有检测到验证、限流或异常页面。

### 6.3 有界完成条件

同时满足以下条件时，才认为当前目标页面已处理完成：

- 评论容器已到末尾；
- 没有可见加载入口；
- 没有加载指示器；
- 连续达到内置的无新增阈值；
- 当前 UI 批次的一级评论均已完成；
- 不存在已确认但尚未处理的回复候选。

达到完成条件后，正式开始模式应保存最终统计、释放锁并停止；不默认通过闹钟刷新页面或自动开启下一轮。

## 7. 回复展开、扫描与删除

### 7.1 展开一个一级评论

回复展开控件必须限定在目标一级评论行内，优先采用稳定结构识别，文案只作为多语言兜底。点击后只在以下任一结果出现时认定成功：

- 新的回复评论 ID 出现；
- 该控件的 `aria-expanded` 从 `false` 变为 `true`；
- 控件所属容器新增可见 `ul` 回复列表；
- 控件被 Instagram 替换，且评论面已稳定并能确认回复列表出现。

未出现可验证结果时，正式模式暂停；Preview 可记录该一级评论无法展开，但不得将其回复视为已经扫描。

### 7.2 当前一级评论范围扫描

扫描只读取当前目标一级评论及其回复的 DOM，并按以下顺序筛选：

1. 只接受具有稳定评论 ID 的回复；
2. 保护帖子作者的评论和回复；
3. 保护白名单用户的回复；
4. 仅保留命中关键词的回复；
5. 以回复深度优先顺序建立当前一级评论的短期候选列表。

不读取或解释页面网络响应，也不把 DOM 节点写入会话检查点。

### 7.3 不使用模拟鼠标的评论菜单

删除前只允许在目标回复行内查找评论选项按钮。定位优先级：

1. 当前回复行内唯一、可见、可连接的评论选项按钮；
2. 当前回复行内唯一、未禁用且结构可确认的评论选项按钮；
3. 当前回复行内唯一且能以多语言无歧义匹配“评论选项/更多选项”的按钮。

排除点赞、回复、翻译、表情、输入、帖子顶部菜单、扩展面板和既有弹层内按钮。确定唯一后仅调用：

```js
menuButton.focus?.();
menuButton.click();
```

不使用 `chrome.debugger`、`Input.dispatchMouseEvent`、`pointerover`、`mouseover` 或 `mousemove`。

如果当前 Instagram 页面将评论选项按钮完全延迟到真实 hover 后才插入 DOM，且目标评论行内不存在可确认按钮，则 DOM-only 路径无法可靠打开菜单。正式模式必须暂停并记录原因，不能猜测、遍历或点击其它按钮。

### 7.4 删除与结果验证

1. 点击评论选项前记录当前所有可见菜单/弹层的快照。
2. 点击后只接受新出现或明确变化的唯一菜单/对话框作为本次动作表面。
3. 只在该表面中查找唯一删除动作；只有“举报/取消”时视为权限不足，不得点击举报。
4. 点击删除后，等待目标回复 ID 消失；如出现新的确认弹层，只能在该新弹层中重新定位唯一删除动作。
5. 目标 ID 消失后，等待评论容器稳定；稳定失败则暂停，不进入下一条。
6. 仅在删除验证明确成功后，才增加 `deleted` 并写入 `processedIds`。

## 8. 异常、暂停与会话

以下任一情况必须立即停止当前串行流程并进入 `paused`：

- 页面显示挑战、验证、限流、登录失效或“稍后重试”；
- 当前账号、内容作者或删除权限无法确认；
- 找不到唯一的回复展开、评论选项、删除或二次确认控件；
- 分页、展开、菜单或删除动作没有产生可验证结果；
- 评论容器被重绘后无法按评论 ID 重新定位；
- 删除已触发但目标 ID 未消失，或删除后页面无法稳定。

Pause 必须取消所有动作节奏等待、DOM 稳定等待和分页等待，保存仅含 ID、统计、状态与时间戳的检查点，并释放任务锁。Stop 清除检查点、取消任何刷新闹钟并且不自动恢复。

本方案不安排完成后的自动刷新续跑；如果后续产品仍需要“下一轮扫描”，应另立方案，默认停留在完成状态并要求明确的用户启动动作。

| `src/content/comment-pagination-loader.js` | 分页前调用统一动作节奏；取消跳过批次休息的末尾探测路径；保留 ID 增长、取消、稳定等待和有界结束判断 |
| `src/content/comment-pagination-surface.js` | 负责评论容器与滚动面发现，并提供可取消的分帧 `scrollToLoadPosition()`；只写入评论容器的 `scrollTop`，分页后重新发现容器，防止虚拟列表导致旧节点继续被使用 |
| `src/content/instagram-control-locator.js` | 明确无 hover 的评论选项按钮定位、唯一性判断和无法定位时的标准失败结果 |

| `src/shared/rate-limiter.js` | 统一记录展开、分页、菜单、删除和确认等动作；锁键和限频键包含平台及规范化目标 |

| `src/platform/instagram/` | 将 Instagram 特有的评论面、展开、菜单、删除与错误判断逐步迁入插件方法；核心只处理标准动作结果和会话状态 |

迁移时遵循现有多平台重构方案：先固定插件输入、输出、错误和副作用，再由核心编排；不得在核心中长期新增 Instagram 文案、选择器或平台专属分支。

## 10. 测试与验收

### 10.1 自动化测试

至少新增或调整以下用例：

1. Preview 展开多个一级评论时不调用删除菜单或删除动作。
2. 正式开始一次只选择一个一级评论；其状态未完成前不得选择下一个。
3. 当前一级评论删除完成并稳定后，才允许展开下一个。
4. 当前 UI 批次所有一级评论完成后，才允许调用分页加载。
5. 展开、分页、菜单、删除和确认均经过统一节奏协调器。
6. Pause/Stop 可取消任意一种动作等待，不会在取消后继续点击。
7. 评论选项按钮在目标回复行内唯一时可直接 `focus()` 与 `click()`。
8. 不存在可确认评论选项按钮时，正式模式返回 `ambiguous` 或 `not-found` 并暂停。
9. 页面中存在帖子顶部菜单、多个更多按钮或多个弹层时，不会选错评论菜单。
10. 新弹层只有举报和取消时，绝不点击举报。
11. 第一次删除后直接消失和出现二次确认弹层都必须正确验证。
12. 删除结果无法确认、容器重绘无法重新定位、验证/限流文案出现时均暂停。
13. `manifest.json` 不再包含 `debugger`，Service Worker 不再注册悬停消息。
14. 无加载入口时只滚动评论容器；`document.body`、`document.documentElement` 和 `window.scrollY` 均不发生滚动。
15. 一次滚动的 `scrollTop` 具有多个单调递增帧值，初末速度低于中段速度，中段保持近似匀速，且总时长落在 360 至 1400 毫秒范围。
16. 滚动期间 `scrollHeight` 增长时，本次仍只到达初始目标；增长后的下一批必须经过稳定、扫描和新的分页动作。
17. Pause/Stop、容器断开或页面重绘会取消后续动画帧，不再向旧容器写入 `scrollTop`。
18. 已处于加载位置时不发生上滚再下滚；仍按加载指示器、入口变化、新 ID 和无增长阈值判断结果。
19. `node --check`、`npm test` 和 `git diff --check` 全部通过。

### 10.2 真实浏览器验收

只能使用测试账号、自己的测试作品和极小批量临时回复。每次验收记录：

- 测试页面与时间；
- 登录账号和内容作者是否一致；
- 测试回复数量、关键词与白名单；
- Preview 的展开数、扫描数、候选数和删除数为 0 的证据；
- 正式模式每个一级评论的展开、删除、稳定和下一单元切换顺序；
- 是否出现验证、限流、菜单缺失、权限不足或 DOM 重绘；
- 实际删除结果与暂停原因。

静态测试与页面 DOM 验证不能证明 Instagram 在真实环境中不会触发限制，也不能替代小批量测试结果。

## 11. 分阶段实施

| 阶段 | 内容 | 完成定义 |
| --- | --- | --- |
| 1 | 先补充本方案所需状态机和动作协调器测试 | 不改删除行为，测试能证明动作按统一入口调度 |
| 2 | 实现正式模式单一级评论串行编排 | 不再跨父评论预建删除队列；Preview 语义不变 |
| 3 | 将分页动作接入统一节奏并移除末尾跳过休息 | 点击或分帧滚动均作为一次可取消动作；滚动只作用于评论容器，具有受控速度曲线和稳定结果判断 |
| 4 | 替换评论菜单路径，移除调试器悬停 | `debugger` 权限、悬停消息与鼠标分发全部删除；菜单不明确即暂停 |
| 5 | 将 Instagram 页面动作迁入插件契约 | `core/` 不读取 Instagram DOM、文案、URL 或错误码 |
| 6 | 小批量真实浏览器验收与文档更新 | 明确记录已验证范围与未验证边界，不宣称规避平台风控 |

每个阶段单独提交、独立可回滚；提交前运行对应测试、语法检查与 `git diff --check`。
