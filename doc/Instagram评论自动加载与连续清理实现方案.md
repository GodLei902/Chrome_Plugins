# Instagram 评论自动加载与连续清理实现方案

## 1. 背景与测试结论

本方案基于 `https://www.instagram.com/p/DcX3YMAgNDh/` 的只读测试结果制定。测试期间只运行了预览和手动滚动，没有点击删除菜单或确认删除。

测试观察到：

- Instagram 的评论容器高度约为 400px，滚动到底部时会懒加载下一批评论。
- 页面中的评论链接数量曾从 27 增加到 42，再增加到 57；重新运行预览后页面继续出现更多已加载节点。
- 测试期间清理器首次预览完成后，手动滚动页面不会自动触发新的扫描，面板统计保持不变；这是本方案要解决的旧行为。
- 当前实现已将分页加载接入 `process()`：预览固定自动加载并继续扫描，正式运行处理完当前批次后自动进入下一批。

因此，当前版本支持“自动滚动加载下一批评论，并继续扫描、筛选和删除”，实现仍不主动请求 Instagram GraphQL 接口，只使用受控的 DOM 评论加载循环。

### 1.1 分页粒度评估

需要区分三种不同的“批次”，不能把它们都称为 10 条或 50 条：

| 层级 | 含义 | 对运行时的要求 |
|---|---|---|
| 主评论接口页 | Instagram 一次网络请求的 `first` 数量；仓库中的抓取记录出现过 `first=50` | 仅作为平台实现事实，运行时不依赖固定值 |
| UI 渲染批次 | 页面滚动后实际追加到 DOM 的评论数量；本次页面测试观察到 15 条一批 | 以新评论 ID 增长判断，不以固定条数判断 |
| 回复分页 | 某个一级评论展开后继续加载的子级回复；数量可能与主评论不同 | 每个父评论单独记录加载状态和无新增次数 |

本次在评论滚动容器 `clientHeight=400`、未展开回复的条件下连续测试，得到以下主评论 ID 数量序列：

```text
首屏 15
滚到底部后 30
滚到底部后 45
滚到底部后 60
滚到底部后 75
滚到底部后 90
```

每次增长均为 15 条，且新增发生在 `scrollTop` 到达 `scrollHeight - clientHeight` 附近时。这个 15 条是当前作品、当前窗口和当前 Instagram 页面实现的实测值，不是平台稳定协议，不能写死到运行逻辑中。回复没有展开，因此上述序列只代表主评论渲染批次。

因此，`batchIndex` 在新实现中应表示“UI 评论 ID 集合发生一次增长”，而不是“第几个接口页”。一次 `first=50` 的网络响应可能被 Instagram 分成多个 UI 渲染批次；反过来，一次滚动也可能没有新增 ID，只是触发了仍在进行中的请求。

仓库抓取记录中的主评论请求确实带有 `first=50`，但该记录同时需要根据 `page_info.has_next_page` 和 `end_cursor` 判断是否还有后续，不能用 50 条直接推断到达末页。当前 DOM-only 运行时不读取接口参数，因此应把这些字段作为诊断和未来适配器的参考，而不是硬编码。

这个分页粒度不会改变总体架构，但会影响以下实现细节：

1. 自动加载器必须把评论容器滚动到 `scrollHeight - clientHeight`，再等待“新 ID 出现”；不能加载一次就认为 50 条已经全部进入 DOM。
2. 主评论加载和父评论回复加载必须分别维护 `lastIds`、`noGrowthAttempts` 和完成原因。
3. 正式删除时，先处理当前已加载父评论下的回复，再滚动到下一个主评论批次，避免回复节点被虚拟列表卸载。
4. 最大批次按“最大 UI 增长轮次”解释；该边界由内置策略维护，不开放给用户配置，另以会话限制避免任务范围失控。
5. 面板应分别显示“累计一级评论”“累计回复”“UI 加载轮次”，不要把“已加载回复”当成主评论总数。

## 2. 目标与边界

### 2.1 目标

1. 自动识别 Instagram 评论滚动容器。
2. 自动点击可见的“加载更多评论/回复”入口。
3. 没有入口时自动滚动到下一批数据触发懒加载。
4. 等待评论 DOM 稳定并检测新评论 ID。
5. 新数据出现后自动继续扫描、筛选和处理。
6. 保留现有回复优先、白名单、帖子作者保护、限频、暂停和失败保护。
7. 预览模式可以完整加载和统计，但永远不执行删除。

### 2.2 不在本次范围内

- 不主动发送或重放 GraphQL/评论接口请求。
- 不拦截、克隆或改写 `fetch`、`XMLHttpRequest` 或媒体响应。
- 不绕过登录、验证码、限流或权限限制。
- 不默认允许在非本人作品上执行正式删除。

## 3. 整体运行流程

```text
检查登录状态与作品权限
  -> 发现评论滚动容器
  -> 等待评论区稳定
  -> 展开当前批次回复和隐藏评论
  -> 扫描当前批次并建立候选
  -> 预览统计或正式处理候选
  -> 等待删除后的容器稳定
  -> 没有候选时加载下一批
  -> 检测新评论 ID
  -> 回到扫描阶段
  -> 连续无新增、达到限制或用户停止后完成
```

### 3.1 到底后的最后一批处理

每次加载出新评论后，业务循环会先安排一次不休息的“末尾探测”，避免最后一批处理完后先进入随机批次休息。探测结果分为两类：

- 仍有新评论 ID：说明页面还可以继续加载，清除探测标记；下一次真正加载恢复批次间随机休息。若这次增长同时触发最大批次限制，先扫描并排空这批新增候选，再停止。
- 没有新增且满足到底条件：继续即时确认，直到连续无增长阈值成立并返回 `completed`。

正式运行中，即使末尾批次存在待删除候选，也会先处理并重新扫描这些候选；候选队列排空后才执行到底确认并停止。末尾没有候选时则直接完成，不再额外等待一轮批次休息。预览同样使用该加载边界，但始终不调用删除逻辑。

加载、扫描和删除必须串行执行，避免 Instagram 重绘时旧候选元素失效。

## 4. 模块设计

### 4.1 新增分页加载器

新增 `src/content/comment-pagination-loader.js`，通过 `globalThis.InstagramCommentPaginationLoader` 暴露加载器工厂。

加载器负责：

- `findScrollableSurface()`：从评论容器向上查找 `overflow-y: auto/scroll` 且 `scrollHeight > clientHeight` 的容器。
- `clickLoadMoreControls()`：复用多语言控件匹配规则，点击当前可见的加载入口。
- `scrollToNextBatch()`：第一版滚动到评论容器底部，触发 Instagram 懒加载；后续再评估是否需要预加载距离。
- `waitForBatchGrowth()`：等待 Mutation、加载指示器结束和新评论 ID 出现。
- `hasReachedEnd()`：结合滚动位置、加载入口、加载指示器和无新增次数判断是否到达末页。
- `cancel()`：响应暂停、停止和任务失效，取消所有等待和观察器。

加载器状态示例：

```js
{
  phase: 'idle',
  batchIndex: 0,
  totalSeen: 0,
  newIds: 0,
  noGrowthAttempts: 0,
  lastScrollTop: 0,
  lastScrollHeight: 0,
  terminalReason: ''
}
```

### 4.2 扩展稳定性模块

在 `src/content/comment-surface-stability.js` 增加滚动后的批次稳定等待，不能只依据 `scrollHeight` 判断加载成功。

一次批次加载成功至少要满足：

1. 评论容器仍连接在当前 document。
2. Mutation 防抖窗口结束。
3. 连续采样稳定。
4. 当前评论 ID 集合出现新增，或已确认加载入口状态发生变化。
5. 加载指示器消失，或等待超时后进入有界重试。

页面使用虚拟列表时，旧评论节点可能被移除；`seenIds` 只能保存身份，不能保存永久有效的 DOM 引用。

### 4.3 清理器主循环

在 `src/content/social-comment-cleaner.js` 中保留现有 `scan()` 和 `remove()` 的安全逻辑，将 `process()` 改为加载器驱动的主循环：

```js
while (任务仍运行) {
  await waitForStableSurface();
  await revealCollapsedComments();

  const result = await scan();

  if (result.candidates.length) {
    if (run.mode === 'preview') {
      // 只统计，不打开菜单，不执行删除。
    } else {
      // 按现有节奏逐条删除，删除后重新稳定并扫描。
    }
    continue;
  }

  if (!(await paginationLoader.nextBatch())) {
    return stop('completed', '当前范围内没有更多可加载评论。');
  }
}
```

正式处理候选时，必须在滚动到下一批之前处理当前批次的候选，避免候选所在节点被虚拟列表卸载。每次删除后按评论 ID 重新定位节点，等待目标节点消失，再重新发现和绑定评论容器。

## 5. 自动加载算法

### 5.1 优先使用页面入口

如果当前评论区域存在“加载更多评论”“查看更多回复”等可见控件，先点击控件并等待新 ID。控件可能只有 `aria-label` 或 SVG `title`，不能只读取按钮文本。

### 5.2 滚动触发懒加载

没有可见加载控件时，滚动评论容器而不是整个页面。本次测试显示只有到达滚动底部才会追加下一批，因此第一版加载器应直接滚动到最大位置：

```js
const targetTop = Math.max(
  0,
  scroller.scrollHeight - scroller.clientHeight,
);
scroller.scrollTo({ top: targetTop, behavior: 'auto' });
```

如果后续页面版本证明接近底部即可预取，再通过配置恢复一个小的预加载距离；不能假设所有 Instagram 页面都在距离底部固定像素处加载。

滚动后记录以下快照：

```js
{
  ids: new Set(visibleCommentLinks().map(commentIdFromUrl)),
  scrollTop: scroller.scrollTop,
  scrollHeight: scroller.scrollHeight,
  hasLoadingIndicator: Boolean(findLoadingIndicator())
}
```

只有在新评论 ID 出现，或加载入口已消失/状态已改变时，才认为本轮加载有效。单纯的容器高度变化不能作为唯一成功条件。

### 5.3 有界完成条件

满足以下条件时停止自动加载：

- 已接近滚动底部；
- 连续 3 次没有新增评论 ID；
- 没有可见加载入口；
- 没有加载指示器；
- 达到最大批次、最长运行时间或用户设置的任务限制。

遇到验证码、限流、网络异常、容器消失或菜单结构不明确时，进入 `paused`，不显示“全部处理完成”。

## 6. 权限与删除安全

当前实现会保护帖子作者的评论，但没有将“当前登录账号是否为作品作者”作为正式运行前置条件。新增正式删除前置检查：

1. 从导航区域识别当前登录账号。
2. 从作品区域识别帖子作者。
3. 两者均已确认且相同，才允许正式删除。
4. 任一账号未知或两者不一致时，只允许预览，正式开始直接暂停并提示权限不明确。

本次测试页面显示当前账号 `godlei_001`，作品作者为 `reindeer.6041291`，因此该页面只能用于预览和加载测试。

现有以下保护必须保持不变：

- 一级评论不进入删除候选。
- 回复优先于一级评论。
- 白名单和帖子作者评论优先跳过。
- 删除前按评论 ID、作者和文本重新校验。
- 删除后等待节点消失和评论区稳定。
- 操作限频、退避、会话时长和删除数量上限继续生效。

## 7. 设置与面板

连续加载不在 `src/options/options.html/js` 提供开关或参数：预览模式固定自动加载但只扫描不删除，正式运行处理完当前批次后固定自动进入下一批。最大批次、连续无新增重试、滚动后稳定等待和批次间随机休息均由内置策略维护。

面板增加：

```text
当前批次：3
本批新增：15
累计发现：57
累计命中：25
无新增重试：0/3
加载状态：正在等待下一批
```

现有“已加载回复”继续表示回复数量，另增“累计发现评论”，避免把回复数量误认为全部评论数量。

## 8. 测试计划

### 8.1 单元测试

- 正确识别评论滚动容器。
- 点击多语言加载入口并等待状态变化。
- 滚动后以新 ID 判断批次增长。
- 连续无新增时有界结束。
- 加载器暂停、停止和取消等待。
- 评论 ID 去重和虚拟列表节点重新定位。
- 加载失败、限流和验证码进入暂停。
- 确认没有安装 `fetch`/`XMLHttpRequest` 观察器。

### 8.2 浏览器预览验收

1. 在本测试页面启用自动加载。
2. 不手动滚动，确认评论 ID 能自动从首批增长到后续批次；当前测试环境预期观察到 `15 -> 30 -> 45 -> 60` 的主评论序列。
3. 面板批次、累计发现和命中数量持续更新；如果窗口或页面实验导致单批不是 15 条，仍应以 ID 增长为准。
4. 展开某个一级评论的回复后，确认回复新增不会被误计为新的主评论批次。
5. 删除菜单、删除确认和评论内容均保持不变。

### 8.3 正式删除验收

使用当前登录账号自己发布的测试视频，准备两批临时关键词回复：

1. 第一批回复按顺序处理。
2. 自动加载第二批并继续扫描。
3. 删除后评论容器重绘仍能继续运行。
4. 达到删除上限后暂停。
5. 非本人作品只能预览，不能进入正式删除。

## 9. 分阶段实施顺序

### 阶段一：自动加载与预览

- 新增分页加载器。
- 接入稳定等待和新 ID 检测。
- 只改造预览模式。
- 完成当前测试页面的浏览器验收。

### 阶段二：正式删除接入

- 将加载器接入正式处理主循环。
- 增加作品权限前置检查。
- 验证删除后重绘、虚拟列表和候选去重。

### 阶段三：设置、恢复与交付

- 增加设置项和面板进度。
- 补充暂停/恢复和任务快照。
- 运行 `node --check`、`npm test`、`git diff --check`，再使用测试账号做小批量真实删除验收。
