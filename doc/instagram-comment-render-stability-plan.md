# Instagram 评论区渲染稳定性与重扫方案

## 1. 文档目的

本文解决两个运行时竞态问题：

1. 从扩展启动目标帖子后，评论数据或评论 DOM 尚未完成渲染，首轮扫描提前执行并得到空结果。
2. 删除一条回复后，Instagram 替换或重建评论列表，下一轮扫描撞在旧节点卸载与新节点挂载之间，任务错误地停滞或提前完成。

本文是后续实现和验收的依据。它只规定评论区的就绪、稳定、重绑和重扫边界，不改变评论筛选规则、白名单、回复优先级、删除节奏或平台权限边界。

## 2. 当前实现与问题定位

当前内容脚本位于 `src/content/social-comment-cleaner.js`：

- `hasRenderedComments()` 通过全页面可见的 `/c/` 链接判断评论是否出现。
- `waitForCondition()` 监听整个 `document.body`，同时以 120ms 定时检查条件。
- 首轮 `scan()` 在评论链接出现后直接解析结构化数据和 DOM 映射。
- 删除确认后固定等待 1300ms，再调用 `scan()`。
- 当前候选为空时，`process()` 会直接结束本轮任务。

这些条件分别存在以下缺口：

### 2.1 首轮扫描过早

Instagram 是异步 SPA。标签页完成加载不代表评论接口、`script[type="application/json"]` 和可见评论节点已经同步完成。出现一个 `/c/` 链接只能证明局部节点出现，不能证明评论数据和评论列表已经稳定。

### 2.2 删除后使用固定时间判断

删除操作可能导致整个回复列表短暂卸载，再挂载一个新的列表容器。1300ms 在网络较快时可能浪费时间，在网络较慢或 Windows Chrome 重绘较慢时又可能不够。固定等待结束时，扫描可能读取到空的中间态。

### 2.3 容器替换导致 Observer 或节点失效

如果 Observer 绑定在被替换的旧容器上，后续变更不会再通知旧 Observer。删除前保存的 `candidate.element` 也不能作为后续操作的可靠引用。

### 2.4 空结果不能直接等同于完成

空结果有三种含义：

- 评论区稳定且确实没有待处理回复。
- 评论区仍在加载或重绘，暂时没有可见候选。
- 数据读取失败、容器丢失或页面状态异常。

这三种状态必须区分处理。

## 3. 最终方案摘要

采用以下组合方案：

1. 动态定位评论容器，而不是固定依赖 Instagram 易变的 class 名。
2. 只对当前评论容器建立 `MutationObserver`；容器被替换时重新发现并绑定。
3. Mutation 发生后执行“防抖 -> 两帧确认 -> 连续稳定快照”流程。
4. 首轮扫描必须满足结构化评论数据和可见评论 DOM 均已出现，并且快照稳定。
5. 删除后等待目标节点消失，再等待新的评论容器稳定，然后重新扫描。
6. 空候选先执行有限次数的稳定等待和重扫；只有稳定为空才结束任务。
7. 删除前按评论 ID 重新定位 DOM，不复用过期的元素引用。
8. Observer 只负责使稳定等待失效或唤醒等待，不直接并发调用 `scan()`。
9. 暂停、停止、超时和容器异常必须取消 Observer、定时器和待执行的帧回调。

## 4. 核心概念

### 4.1 评论容器（comment surface）

评论容器是当前帖子中承载一级评论和已展开回复的最小稳定 DOM 作用域。不能把整个 `document.body` 作为评论容器。

发现策略按以下优先级执行：

1. 从可见的 `/c/<comment-id>/` 链接出发，向上检查有限层级的祖先节点。
2. 优先选择同时包含多个评论链接、评论作者文本和评论操作控件的祖先节点。
3. 只有一个评论链接时，选择包含该链接及其评论行操作控件的最近可见祖先。
4. 对发现结果保存节点引用和 `surfaceGeneration`。节点断开后必须重新发现，不能继续使用旧引用。

Instagram 页面结构变化时，选择器只作为候选信号；最终必须通过可见评论链接、评论 ID 数量和节点连接状态校验。

### 4.2 数据快照（data snapshot）

结构化数据快照用于判断评论数据是否已经出现和是否发生变化，至少包含：

- `XDTCommentDict` 的评论 ID 集合；
- 每个 ID 的 `parent_comment_id`；
- `child_comment_count`；
- 结构化评论总数。

快照必须排序后再生成签名，避免对象遍历顺序变化造成误判。

### 4.3 DOM 快照（DOM snapshot）

DOM 快照只采集当前评论容器内的稳定身份信息，至少包含：

- 可见 `/c/<comment-id>/` 链接 ID；
- 已映射回复的作者和归一化文本摘要；
- 容器是否仍连接到当前 document；
- 当前 `surfaceGeneration`。

不把 class 名、React 临时属性、按钮排序或完整 `innerHTML` 放入签名，避免无关变化导致永远无法稳定。

### 4.4 稳定状态

一次稳定确认必须同时满足：

- 评论容器存在且 `isConnected`；
- 容器内至少存在一个可见评论身份信号；
- 首轮扫描时结构化评论数据数量大于零；
- 防抖窗口内没有新的相关 Mutation；
- 两次连续采样的 `data snapshot + DOM snapshot` 相同；
- 两次采样期间 `surfaceGeneration` 未变化。

删除后的稳定确认不要求结构化 JSON 必须同步删除目标 ID，因为 Instagram 可能保留旧 JSON；删除结果以目标 DOM 节点消失和新容器稳定为准。

## 5. Observer 与稳定等待设计

### 5.1 Observer 范围

绑定到评论容器时观察：

- `childList: true`；
- `subtree: true`；
- `characterData: true`；
- `attributes: true`，并优先限制到 `aria-expanded`、`hidden`、`style`、`class` 等会影响可见性或控件挂载的属性。

Observer 回调不执行扫描，只做三件事：

1. 增加 `mutationVersion`；
2. 标记当前稳定结果失效；
3. 重置防抖定时器。

### 5.2 容器重绑

当前容器断开、评论链接全部消失或 `surfaceGeneration` 发生变化时：

1. 断开旧容器 Observer；
2. 在短时间内启用一次 document 级别的发现 Observer；
3. 重新执行评论容器发现；
4. 找到新容器后增加 `surfaceGeneration`，绑定新 Observer；
5. 从稳定快照流程重新开始。

document 级 Observer 只用于“找回容器”，找到新容器后立即断开，不能长期监听整个页面。

### 5.3 防抖与两帧确认

推荐默认值：

| 参数 | 默认值 | 说明 |
|---|---:|---|
| `mutationDebounceMs` | 250ms | 最后一次相关 Mutation 后等待页面停止连续修改。 |
| `rafConfirmCount` | 2 | 防抖结束后连续等待两次 `requestAnimationFrame`。 |
| `stablePasses` | 2 | 两次快照签名相同且版本未变化才确认稳定。 |
| `initialReadyTimeoutMs` | 15000ms | 首次评论区就绪最大等待时间。 |
| `postDeleteSettleTimeoutMs` | 10000ms | 删除后新容器稳定最大等待时间。 |
| `emptyRescanAttempts` | 3 | 空候选时最多追加的稳定重扫次数。 |

如果页面处于后台导致 `requestAnimationFrame` 延迟，必须提供短定时器兜底，但不能绕过稳定快照条件。

稳定等待的逻辑约束如下：

```text
发现或重新绑定评论容器
  -> 等待防抖窗口结束
  -> 等待两帧
  -> 读取数据快照和 DOM 快照
  -> 再次等待防抖窗口和两帧
  -> 读取第二份快照
  -> 签名相同且 mutationVersion/surfaceGeneration 未变化：稳定
  -> 否则重新开始，直到成功或超时
```

## 6. 首次启动流程

首次启动和恢复启动均使用以下顺序：

```text
校验目标 URL 和运行锁
  -> 发现评论容器
  -> 绑定容器 Observer
  -> 等待结构化数据、可见 DOM 和稳定快照
  -> 展开“查看回复/隐藏评论”等入口
  -> 再次等待评论容器稳定
  -> 扫描并建立候选
  -> 预览结束，或进入正式处理
```

首轮不能再使用“发现一个可见 `/c/` 链接后立即扫描”作为唯一条件。

如果首轮稳定等待超时：

- 不得显示“已完成”；
- 任务进入 `paused`；
- 面板显示“评论区在规定时间内未完成渲染”；
- 保留诊断信息，包括等待阶段、容器发现次数、Mutation 次数和最后一次快照摘要。

## 7. 删除后流程

删除一条回复的完整流程：

```text
从候选 ID 重新定位当前 DOM
  -> 校验作者、文本和评论 ID
  -> 打开评论菜单并确认删除
  -> 等待目标评论节点消失
  -> 检查评论容器是否被替换
  -> 必要时重新发现并绑定容器
  -> 等待新容器稳定
  -> 重新扫描并重建候选队列
```

删除确认应优先使用评论 ID 对应节点消失；文本消失只作为兼容性回退，并且必须经过作者和容器范围校验。

删除前的 `candidate.element` 仅作为临时缓存，不是身份依据。每次实际操作前必须重新定位，避免 Instagram 重绘后点击旧节点。

如果目标节点已消失但稳定等待超时：

- 该次删除可以计入已确认删除数；
- 不得继续执行下一条删除；
- 任务进入 `paused`，提示“已确认删除，但评论区未稳定”；
- 用户恢复任务时重新发现容器并扫描。

## 8. 空结果保护

扫描结果为空时，必须先判断评论区状态：

### 8.1 稳定为空

满足以下条件后才允许完成：

- 评论容器稳定；
- 结构化数据和 DOM 快照稳定；
- 已执行折叠回复/隐藏评论入口展开；
- 已完成规定次数的空结果重扫；
- 没有容器重绑、Mutation 风暴、数据加载失败或页面异常。

此时可以显示：

```text
已完成：当前稳定评论容器中没有待处理回复。
```

### 8.2 暂时为空

如果稳定等待尚未完成、容器刚刚替换或最近仍有 Mutation：

- 保持扫描状态；
- 等待稳定后重扫；
- 不清空会话级 `seenIds`、`processedIds`；
- 不增加跳过数或完成状态。

### 8.3 异常为空

如果容器在超时时间内无法恢复、结构化数据损坏或页面出现验证/限流提示：

- 进入 `paused`；
- 不执行任何猜测性删除；
- 面板显示明确原因。

## 9. 运行状态机

```text
idle
  -> waiting-surface
  -> expanding
  -> stabilizing
  -> scanning
  -> running
  -> waiting-delete
  -> stabilizing
  -> scanning

stabilizing --稳定为空--> completed
stabilizing --超时/容器异常--> paused
running --菜单或权限不可靠--> paused
任意等待状态 --用户暂停--> paused
任意状态 --用户停止--> idle
```

状态语义：

- `waiting-surface`：寻找或重新绑定评论容器。
- `expanding`：点击折叠回复或隐藏评论入口。
- `stabilizing`：执行防抖、两帧和快照确认。
- `waiting-delete`：等待删除目标消失或列表替换完成。
- `completed`：仅表示稳定评论容器中没有待处理候选。
- `paused`：页面状态不可靠，需要用户恢复或检查页面。

## 10. 并发、取消与旧结果保护

Observer 不能直接启动并发扫描。实现必须提供以下保护：

- `scanInFlight` 或等价互斥标记，保证同一时间只有一个扫描流程。
- `surfaceGeneration`，拒绝旧容器的观察结果。
- `scanGeneration`，扫描开始后如果任务暂停、停止或容器替换，旧结果不得写回当前候选队列。
- 统一取消函数，清理 Observer、防抖定时器、`requestAnimationFrame` 回调和等待 Promise。
- `stop()` 和 `pause()` 后，即使之前的异步等待完成，也不能触发下一次删除。

## 11. 失败处理

| 情况 | 行为 |
|---|---|
| 首次评论容器未出现 | 等待至 `initialReadyTimeoutMs`，超时暂停。 |
| 评论容器被替换 | 断开旧 Observer，重新发现并绑定，重新稳定确认。 |
| Mutation 持续发生 | 不把中间态当作空结果，直到稳定或超时。 |
| 删除目标已消失但列表未稳定 | 计入已确认删除，暂停后续操作。 |
| 菜单、删除按钮无法可靠识别 | 立即暂停，不猜测点击。 |
| 结构化数据解析失败 | 暂停当前任务并显示数据异常，不执行删除。 |
| 验证、限流或挑战页面 | 立即暂停，不重试删除。 |
| 稳定为空 | 完成本轮任务，允许用户手动加载下一批后重新开始。 |

## 12. 实现边界

本方案明确不采用以下方式作为主流程：

- 仅增加固定等待时间；
- 长期监听整个 `document.body`；
- 仅依赖 `requestAnimationFrame`；
- 依赖 Instagram React 内部 Fiber 或未公开事件；
- 通过网络拦截代替 DOM 稳定确认；
- 在 Observer 回调中直接调用删除或扫描。

网络数据仍可作为结构化评论来源，但“可执行删除”必须同时满足当前页面 DOM 已稳定、目标节点身份可确认和菜单控件可可靠定位。

## 13. 测试与验收

### 13.1 自动化测试

应为稳定等待和快照逻辑补充可注入的测试接口或独立纯函数，覆盖：

1. 页面初始无评论，随后分批插入评论数据和 DOM，首轮不会得到错误空结果。
2. DOM 在两帧之间继续变化时，不会提前确认稳定。
3. 两次快照内容相同但容器被替换时，不会复用旧容器结果。
4. 删除后旧列表整体移除、新列表重新挂载时，Observer 能重新绑定。
5. 删除后短暂空列表不会触发 `completed`。
6. 稳定为空经过规定重扫次数后才完成。
7. 容器稳定超时进入 `paused`，而不是 `completed`。
8. 暂停或停止后，延迟完成不会启动下一次扫描或删除。
9. 同一时间触发多个 Mutation 时，只产生一个串行稳定等待流程。
10. 折叠回复展开造成 Mutation 后，会重新执行稳定确认。

### 13.2 浏览器验收

在 Windows Chrome、测试账号和临时评论上执行：

1. 从扩展按钮启动一个评论尚未显示的目标帖子，确认首轮扫描能等待到有效结果。
2. 预览阶段确认不会点击菜单或删除。
3. 删除一条回复，观察评论列表被替换时任务不会停滞或误报完成。
4. 连续删除至少两条回复，确认每条删除前都重新定位当前 DOM。
5. 删除后手动加载下一批评论，再次开始，确认新容器可以被发现。
6. 模拟或观察折叠回复、隐藏评论展开，确认展开后会再次等待稳定。
7. 在评论区持续加载或页面异常时，确认任务暂停并显示原因。

验收记录必须区分：

- 静态检查和单元测试；
- 模拟 DOM 稳定性测试；
- Windows/Instagram 真实页面 Preview；
- 小批量真实删除。

静态测试通过不能替代真实 Instagram 页面验证。

## 14. 推荐实现顺序

1. 抽取评论容器发现、快照签名和稳定等待模块。
2. 将首轮 `hasRenderedComments()` 替换为稳定评论区就绪门禁。
3. 在删除后接入目标消失确认、容器重绑和稳定等待。
4. 增加空结果重扫保护，禁止中间态直接完成。
5. 增加扫描序列号、取消逻辑和 Observer 生命周期管理。
6. 完成自动化测试、`node --check`、`node --test test/*.test.js` 和 `git diff --check`。
7. 使用测试账号执行 Preview，再进行小批量真实删除验收。
