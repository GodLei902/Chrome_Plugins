# （已废弃）Instagram 评论接口响应筛选与 DOM 删除落地方案

> 当前实现已改为纯 DOM 方案，详见 [instagram-comment-dom-only-plan.md](./instagram-comment-dom-only-plan.md)。本文件仅保留为历史记录，不再作为实现依据。

## 1. 文档目的

本文确定 Instagram 评论清理器后续的运行边界：

```text
自动点击一级评论的回复入口
  -> 触发 Instagram 自己的子级评论请求
  -> 被动监听接口响应
  -> 用接口数据建树、筛选和过滤
  -> 生成完整候选队列
  -> 删除阶段再展开和操作 DOM
```

本方案解决以下问题：

1. 子级评论接口响应尚未完成，脚本已经开始读取 DOM，导致扫描结果为空或不完整。
2. 页面已经显示多条子级评论，但 DOM 链接映射只识别到其中一条。
3. 第二次预览依赖当前 DOM 或会话新增数量，显示的扫描数量不等于当前完整评论数量。

本方案不恢复一级评论滚动分页，不由扩展主动请求 Instagram GraphQL 接口，也不改变关键词、白名单、帖子作者保护、删除节奏和权限边界。

## 2. 已确认的产品要求

### 2.1 扫描阶段

- 自动点击“查看回复”“显示全部回复”等入口。
- 点击仅用于触发 Instagram 页面原本的请求。
- 扩展不主动构造或发送子级 GraphQL 请求。
- 扫描、建树、关键词匹配、白名单判断全部使用接口响应数据。
- 不使用 DOM 文本作为评论主数据源。
- 所有待加载父评论完成或明确失败后，才生成最终候选队列。

### 2.2 删除阶段

- 候选生成完成后才开始删除。
- 删除前根据 `parent_comment_id` 找到父评论 DOM。
- 必要时再次展开该父评论的回复。
- 等待目标 `replyId` 对应的 DOM 节点出现。
- 校验评论 ID、作者和文本后再打开菜单删除。
- 删除后等待目标节点消失和评论容器稳定。

### 2.3 明确不做

- 不自动滚动加载后续一级评论。
- 不自动请求子级游标分页。
- 不通过扩展自己的 `fetch()` 补发接口请求。
- 不在接口响应缺失时根据 DOM 猜测评论内容。
- 不在数据未完成时执行删除。

## 3. 可行性结论

### 3.1 总体结论

方案技术上可行，推荐实施。

可行性的前提是 Instagram 当前页面使用可观察的 `fetch` 或 `XMLHttpRequest` 发起评论请求，并且扩展能够在请求发出前安装页面上下文监听器。

### 3.2 可行性评估

| 项目 | 评估 |
|---|---|
| 扩展不主动发请求 | 可行 |
| 被动读取评论响应 | 可行，但必须尽早注入监听器 |
| 接口数据建树和筛选 | 可行性高 |
| 删除前 DOM 展开和定位 | 可行，继续使用 MutationObserver |
| 第二次预览复用接口缓存 | 可行 |
| Instagram 长期兼容性 | 中等，内部接口和传输方式可能变化 |
| 风控风险 | 低于扩展主动请求，但自动点击和删除仍有行为风险 |
| 实现复杂度 | 中高 |
| 是否需要真实页面验收 | 必须 |

### 3.3 被动监听的限制

被动监听只能取得页面已经发出的响应。如果父评论没有被展开，页面没有发出子级请求，扩展也不会凭空获得子级数据。因此扫描阶段仍需要自动点击回复入口作为请求触发器。

如果监听器注入太晚，页面初始请求可能已经完成。扩展更新后首次测试应刷新 Instagram 页面，确保监听器在评论请求之前安装。

## 4. 总体架构

### 4.1 页面上下文响应监听器

新增独立脚本 `src/content/instagram-response-observer.js`：

- `run_at: document_start`；
- `world: MAIN`；
- 包装页面的 `fetch` 和 `XMLHttpRequest`；
- 只读取匹配评论 GraphQL 的响应；
- 使用 `Response.clone()`，不消费或修改页面原始响应；
- 通过 `window.postMessage` 向隔离世界发送规范化事件。

监听器不修改请求参数、请求头、响应内容或页面业务逻辑。

### 4.2 隔离世界数据接收器

`src/content/social-comment-cleaner.js` 接收并校验响应事件：

1. 校验 `event.source === window`；
2. 校验消息来源标识和当前页面 origin；
3. 校验 payload 是否包含有效的 `XDTCommentDict` 节点；
4. 按媒体 ID、父评论 ID和评论 ID 去重；
5. 更新接口响应缓存；
6. 唤醒等待中的扫描流程。

页面消息只能提供数据，不能直接触发删除、暂停或其他扩展动作。

### 4.3 为什么不使用 `webRequest`

MV3 的 `webRequest` 适合观察请求元数据，但不能稳定地直接取得响应正文。本方案需要解析 `XDTCommentDict` 和 `parent_comment_id`，因此使用页面上下文的 `fetch/XHR` 只读包装。

## 5. 接口响应识别与数据结构

### 5.1 一级评论响应

主列表节点路径参考：

```text
data.xdt_api__v1__media__media_id__comments__connection.edges[].node
```

需要读取：

- `pk`；
- `user.username`；
- `text`；
- `parent_comment_id`；
- `child_comment_count`；
- `__typename`。

### 5.2 首次子级响应

子级节点路径参考：

```text
data.xdt_api__v1__media__media_id__comments__parent_comment_id__child_comments__connection.edges[].node
```

需要读取：

- `pk`；
- `user.username`；
- `text`；
- `parent_comment_id`；
- `child_comment_count`；
- `__typename`。

响应识别优先使用字段路径和节点类型，`doc_id` 只作为诊断或兼容提示，不能把单个固定 ID 作为唯一判断条件。

### 5.3 父评论缓存

```js
childReplyCache[parentId] = {
  mediaId: '',
  status: 'pending',
  expectedCount: 0,
  replies: [],
  hasNextPage: false,
  endCursor: null,
  error: '',
  responseAt: 0,
};
```

状态含义：

- `pending`：已点击展开，等待接口响应；
- `ready`：响应已收到，子级数据完整；
- `partial`：响应返回但仍有未请求的分页或数量不完整；
- `error`：响应解析失败、父 ID 不匹配或等待超时。

## 6. 扫描流程

### 6.1 初始扫描

```text
校验目标 URL 和运行锁
  -> 安装/确认响应监听器
  -> 读取一级评论接口数据
  -> 建立父评论列表
  -> 筛选 child_comment_count > 0 的父评论
  -> 逐个自动点击回复入口
  -> 等待对应 parent_comment_id 的接口响应
  -> 合并所有接口数据
  -> 建树和过滤
  -> 生成候选队列
```

### 6.2 自动点击展开

入口识别必须覆盖当前已知界面语言：

- 中文：查看回复、查看全部回复；
- 英文：View replies、See all replies、View more replies；
- 日文：`1件すべての返信を見る`、`返信をすべて見る`、相关隐藏评论入口。

搜索范围使用父评论节点及有限层级祖先，避免被新容器替换或入口位于相邻节点影响。

每次点击后不立即读取 DOM 作为数据，而是等待：

1. 对应父评论接口响应；
2. 接口节点的 `parent_comment_id` 与父评论 ID 一致；
3. 接口返回状态达到 `ready` 或明确 `partial/error`。

### 6.3 扫描完成条件

只有以下条件满足时才允许进入过滤完成状态：

- 没有 `pending` 父评论；
- 所有成功响应已合并；
- 失败父评论已记录并从删除候选中排除；
- 评论树中的回复 ID 已去重；
- 过滤规则已执行完成。

扫描结果统计拆分为：

- 当前接口已加载子级数；
- 当前命中候选数；
- 等待响应父评论数；
- 加载失败父评论数；
- 本次会话新增 ID 数。

“当前接口已加载子级数”不能再用 `seenIds` 的新增数量代替。

## 7. 删除流程

### 7.1 候选数据

每个候选必须携带：

- `id`：子级评论 ID；
- `parentId`：一级评论 ID；
- `username`；
- `text`；
- `kind: 'reply'`。

### 7.2 删除前 DOM 准备

```text
按 parentId 找到父评论 DOM
  -> 必要时点击该父评论的回复入口
  -> MutationObserver 等待目标 replyId 节点出现
  -> 重新定位当前节点
  -> 校验作者和归一化文本
```

不能复用扫描阶段保存的旧 DOM 引用。评论容器被 Instagram 替换后，必须按 ID 重新定位。

### 7.3 删除后确认

删除确认优先判断目标评论 ID 对应节点消失，文本消失只作为兼容性回退。

确认删除后：

1. 更新 `processedIds`；
2. 从当前缓存和候选队列移除目标 ID；
3. 等待评论容器稳定；
4. 再处理下一条候选。

如果删除已确认但容器无法稳定，任务必须暂停，不能继续下一条删除。

## 8. 第二次预览语义

第二次预览不能依赖“当前 DOM 可见数量”。流程应为：

```text
复用当前媒体的接口响应缓存
  -> 合并一级评论和子级评论
  -> 排除 processedIds
  -> 重新执行规则过滤
  -> 更新当前扫描数和候选数
```

接口缓存只在以下情况清理：

- 目标帖子 URL 改变；
- 页面刷新后上下文失效；
- 用户明确停止并开始新的目标会话。

同一目标页面的重复预览不应因为 DOM 重建而丢失已收到的接口响应。

## 9. 状态和失败处理

推荐状态：

- `waiting-surface`：等待评论容器出现；
- `expanding`：自动点击回复入口；
- `waiting-response`：等待父评论接口响应；
- `scanning`：接口数据建树和过滤；
- `running`：执行删除；
- `waiting-delete`：等待目标 DOM 消失或容器稳定；
- `paused`：数据或页面状态不可靠；
- `completed`：当前接口数据中没有待处理候选。

失败行为：

| 情况 | 行为 |
|---|---|
| 监听器注入太晚 | 提示刷新页面，不把当前结果标记为完整 |
| 父评论响应超时 | 标记该父评论失败，不删除其子级 |
| 返回父 ID 不匹配 | 丢弃该响应，暂停该父评论 |
| 返回 `has_next_page=true` | 标记 `partial`，不假装全部加载 |
| 接口数据完整但 DOM 未出现 | 删除阶段等待，超时后暂停 |
| 删除目标已消失但容器未稳定 | 计入确认删除，暂停后续删除 |
| Mutation 持续发生 | 不把暂时空结果视为完成 |

## 10. 风控与兼容性评估

### 10.1 相比扩展主动请求的优势

- 不额外制造 GraphQL 请求；
- 不需要复制请求参数、Cookie 或内部请求头；
- 请求节奏由 Instagram 页面自身控制；
- 监听器只读取响应，不修改请求和响应。

### 10.2 仍然存在的风险

- 自动点击大量回复入口属于页面行为；
- 自动删除行为本身仍可能触发平台限制；
- 页面可以检测到 `fetch/XHR` 包装；
- Instagram 可能更换内部传输方式或响应结构；
- 监听器未及时注入时无法恢复过去的响应正文。

本方案降低额外请求风险，但不能保证绕过 Instagram 风控，也不应以绕过风控为目标。

## 12. 自动化测试

至少覆盖：

1. 主评论响应可提取任意数量一级评论；
2. 子级响应按 `parent_comment_id` 正确归属；
3. 重复响应按评论 ID 去重；
4. `child_comment_count=0` 不需要点击展开；
5. 多个父评论响应按串行顺序完成；
6. 响应延迟期间不会提前生成候选；
7. 响应失败的父评论不会进入删除队列；
8. 第二次预览从缓存重新得到完整两条子级；
9. `has_next_page=true` 标记部分加载；
10. 删除阶段必须等待目标 DOM 节点出现；
11. 容器替换后按 ID 重新定位；
12. 暂停/停止后延迟响应不能继续触发删除。

## 13. 浏览器验收

使用测试账号和临时评论验证：

1. 页面首次加载后刷新，确保监听器早于评论请求安装；
2. 自动点击一级评论回复入口；
3. 预览统计与接口返回子级数量一致；
4. 页面 DOM 尚未完整显示时，扫描仍能取得完整接口数据；
5. 两个父评论各有一个子级时，第二次预览仍显示两条；
6. 接口筛选完成前不触发删除；
7. 删除时才展开目标父评论 DOM；
8. 容器替换后仍能按 ID 定位并确认删除；
9. 响应失败或超时进入暂停，而不是显示完成；
10. 不自动滚动加载后续一级评论。

静态检查通过不能替代真实 Instagram 页面验证。

## 14. 最终结论

该方案可行，且比“等待 DOM 稳定后直接扫描”更适合当前 Instagram 页面。

推荐正式实现以下组合：

```text
页面自动点击展开
  + 被动监听接口响应
  + 接口数据建树和过滤
  + 删除阶段按 ID 展开和定位 DOM
  + MutationObserver 只负责 DOM 等待和重绘确认
```

主要技术难点是早期安装监听器、按父评论 ID 等待完整响应，以及正确区分 `pending/ready/partial/error`，不需要扩展主动调用 Instagram 接口。
