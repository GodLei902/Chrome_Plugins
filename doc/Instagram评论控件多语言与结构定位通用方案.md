# Instagram 评论控件多语言与结构定位通用方案

## 1. 背景

Instagram 的评论区会根据账号、浏览器和实验分组显示不同语言的“查看回复”“隐藏回复”“加载更多”“评论选项”和“删除”文案。当前清理器在 DOM-only 模式下通过页面点击触发回复渲染和删除菜单，因此所有评论控件的定位都不能依赖某一种语言。

本方案覆盖回复展开、隐藏评论展开、分页加载、评论选项菜单和删除确认等控件。目标是在不读取 Instagram 私有接口、不主动发起请求的前提下，把主定位路径调整为“评论行范围 + 稳定元素结构 + 状态变化确认”，并把多语言文案集中放入配置文件。定位优先使用元素和结构；元素找不到时，严格按“日语 -> 中文 -> 其他语言/通用兜底”的顺序匹配文案。

## 2. 现场验证结论

2026-08-25 在 Chrome 的 Instagram 中文（简体）页面上进行了只读 DOM 分析，并悬停观察了评论选项按钮、展开控件和帖子顶部菜单。未执行删除操作。

现场出现的控件文案包括：

- `查看所有1条回复`
- `查看所有2条回复`
- `查看所有3条回复`

当前 `src/content/social-comment-cleaner.js` 的正则分别覆盖“查看所有回复”和“查看 2 条回复”，但不覆盖“查看所有2条回复”。因此，中文页面漏掉展开入口是当前实现的真实兼容性缺陷。

现场控件结构为：

```html
<div role="button" tabindex="0">
  <div>
    <div></div>
    <span>查看所有2条回复</span>
  </div>
</div>
```

当前页面的观察结果：

1. 页面中共有 40 个可见 `[role="button"]`。
2. 符合“按钮 -> 内层容器 -> 空 div + 文本 span”结构的控件共有 5 个，全部对应回复展开入口。
3. 普通“回复”按钮的结构是“按钮 -> 文本 span”，没有空的前置 div。
4. 展开一个结构匹配的控件后，文案变为“隐藏所有回复”，其父容器新增 `ul` 回复容器；这提供了与语言无关的点击结果信号。
5. Instagram 的 CSS class（例如 `x1xp9za0`）在不同版本中可能变化，不能作为唯一定位条件。

评论选项按钮的现场结构为：

```html
<div role="button" tabindex="0">
  <div>
    <svg role="img" aria-label="评论选项" title="评论选项" viewBox="0 0 24 24">
      <circle></circle><circle></circle><circle></circle>
    </svg>
  </div>
</div>
```

该按钮有以下重要特征：

1. 外层按钮有 `role="button"` 和 `tabindex="0"`，但没有自己的 `aria-label`。
2. “评论选项”位于子级 SVG 的 `aria-label` 和 `<title>` 中，因此标签读取必须递归子节点。
3. 按钮只在悬停评论后显示；悬停前不能把“按钮不存在”当作页面异常。
4. 帖子顶部也有“更多选项”按钮，且带 `aria-haspopup="dialog"`。因此不能在整个页面按文案找第一个“更多”，必须先限制到目标评论行。
5. 评论选项图标是水平三个点的 SVG；图标几何结构只能作为弱特征，不能依赖 Instagram 动态 class 或固定像素。

以上结果说明，提供的横线 div 可以作为结构特征的一部分，但不应直接依赖它的 class 名。

## 3. 当前实现分析

### 3.1 评论控件扫描

`src/content/social-comment-cleaner.js` 当前流程如下：

1. `revealCollapsedComments()` 在评论面祖先和 `document` 范围内查找 `button,[role="button"]`。
2. `controlLabels()` 读取按钮文本、自身 `aria-label`、`title` 以及子元素的 `aria-label/title`。
3. `isCommentExpansionControl()` 使用 `replyExpander`、`hiddenCommentExpander` 和 `loadMoreExpander` 三个固定正则决定是否点击。
4. 点击后只等待控件文案变化或出现新的评论 ID。

删除路径目前另外执行以下定位：

1. `locateCommentElement()` 先按评论 ID、作者和正文重新找到评论行。
2. `revealCommentMenu()` 派发 DOM 悬停事件，`hoverCommentWithBrowserPointer()` 再通过真实鼠标移动触发 Instagram 的 hover UI。
3. `commentMenuFor()` 只在目标评论元素内部查询按钮，先读取菜单文案，再用“包含 SVG 且尺寸较大”的按钮作为降级候选。
4. `visibleDeleteDialog()` 在可见 `[role="dialog"]` 中寻找删除文案，`deleteButtonInDialog()` 再点击删除项。

因此，当前代码已经具备“评论行范围”和“子元素标签读取”两个基础，但展开、评论选项和删除确认仍没有共用定位器，也没有统一的多语言配置文件。

相关位置：

- `src/content/social-comment-cleaner.js:21-38`：多语言正则与标签读取。
- `src/content/social-comment-cleaner.js:358-389`：折叠评论/回复入口扫描与点击。
- `src/content/social-comment-cleaner.js:526-537`：删除前重新展开目标回复。

### 3.2 主要问题

#### 文案模板不完整

“查看所有2条回复”这类数字插入位置变化会绕过当前正则。即使继续增加语言，也会不断遇到数字、空格、标点和实验文案变化。

#### 两套定位逻辑不一致

扫描阶段使用 `controlLabels()`，会读取子元素的 `aria-label/title`；`ensureReplyDom()` 只读取按钮自身文本或自身属性，可能出现扫描时能找到、删除前重新展开时找不到的情况。

#### 结构语义没有被利用

当前实现已经查找 `[role="button"]`，但没有利用 `tabindex`、子节点形状、同级 `ul`、评论行边界等信息。提供的空 div/文本 span 结构因此没有发挥作用。

#### 评论正文排除仍依赖语言

`rowCommentText()` 通过排除若干已知控件文案来构造评论正文。未知语言的展开控件可能混入评论文本，导致关键词误判。

#### 评论选项的降级条件过宽

`commentMenuFor()` 的 SVG 降级条件可能把评论行内其他图标按钮误认为菜单。当前中文页面中，评论选项按钮的标签在 SVG 子节点而非外层按钮；如果未来标签被移除，仅凭尺寸和“不是点赞”仍不足以确认用途。

#### 文案没有集中管理

展开、评论选项和删除确认分别在内容脚本中维护正则。新增语言或 Instagram 文案变化时容易遗漏其中一条路径，也无法明确控制“先匹配日语、再匹配中文”的优先级。

#### 删除文案和弹层状态不完整

当前 `deleteLabel` 只匹配 `delete`、`删除`、`刪除`、`削除` 及少量后缀，不能覆盖 `コメントを削除`、`コメントを削除する`、`删除评论`、`刪除留言` 等常见完整短语；同时 `visibleDeleteDialog()` 只从可见 `role="dialog"` 中查找文本，没有递归读取 `aria-label/title`，也没有记录弹层是否由本次评论菜单点击新产生。

#### 未区分权限分支和定位异常

自有评论菜单可以出现 `删除`，他人评论菜单可能只有 `举报`、`取消`。两者都能成功打开弹层，但处理含义不同：弹层存在且没有删除动作时应记录权限不足或评论不属于当前账号，不能继续猜测；弹层本身未出现才属于菜单定位异常。

#### 未覆盖二次确认流程

当前 `remove()` 打开评论菜单后找到第一个删除按钮并直接点击，然后等待目标消失。如果 Instagram 版本在第一次点击后再显示确认弹窗，现有流程不会再次定位确认按钮，可能停在弹窗上或把未完成操作当成失败。

## 4. 目标与边界

### 目标

- 统一覆盖回复展开、隐藏评论展开、分页加载、评论选项菜单和删除确认。
- 支持中文、繁体中文、日文、英文及未知语言；元素结构优先，元素找不到时按日语、中文、其他语言的顺序匹配文案。
- 建立独立的多语言文案配置文件，定位逻辑不再散落硬编码正则。
- 不依赖 Instagram 动态 CSS class。
- 扫描阶段、删除前重展开阶段和删除菜单阶段使用同一个定位器。
- 继续使用当前 DOM-only 策略，不改写 `fetch`/`XMLHttpRequest`，不主动调用 Instagram 接口。
- 发生结构不确定或点击结果不明确时暂停，不盲目点击。

### 非目标

- 不保证识别 Instagram 所有未来实验 UI。
- 不通过 class 名、React 私有属性或内部接口恢复稳定性。
- 不在无法确认控件用途时遍历点击所有 `role=button`。
- 不把语言配置文件当作结构定位的替代品；文案只负责元素缺失时的兼容兜底。

## 5. 建议的定位策略

### 5.1 第一级：语义和评论行范围

在当前评论行或其有限祖先范围内收集：

```css
button,
[role="button"],
[tabindex="0"][aria-expanded],
[tabindex="0"][aria-controls]
```

候选必须满足：

- 节点已连接且可见；
- 位于包含一个 `/c/<comment-id>` 链接的评论行范围内，或位于评论面分页区域；
- 不是输入框、可编辑区域、菜单弹层或删除确认弹层中的按钮。

评论选项和删除控件必须额外满足：

- 评论选项候选必须位于目标评论行内；禁止从 `document` 根节点直接取第一个“更多”按钮。
- 删除候选必须位于点击评论选项后出现的可见菜单/对话框内；禁止在原评论行或整页文本中寻找“删除”。
- 若候选带有 `aria-haspopup="dialog"`，只有在它属于目标评论行时才可作为评论选项；帖子头部同属性按钮必须排除。

### 5.2 第二级：结构匹配

对提供的 Instagram 版本，使用不依赖文字内容的结构特征：

```text
可见 button/[role=button]
  └─ 第一层容器恰好有两个子元素
      ├─ 空 div（无文本、无子节点）
      └─ 文本元素（通常为 span）
```

空 div 的宽高可以作为弱校验（当前页面约为 22×1 px），但不能把具体 class 或固定像素作为唯一条件。

概念伪代码：

```js
function isReplyDisclosureShape(node) {
  const wrapper = node?.firstElementChild;
  const marker = wrapper?.firstElementChild;
  const label = wrapper?.lastElementChild;
  if (!node?.matches?.('button,[role="button"]')) return false;
  return Boolean(
    wrapper?.children.length === 2 &&
    marker?.tagName === 'DIV' &&
    marker.children.length === 0 &&
    !(marker.textContent || '').trim() &&
    label?.tagName === 'SPAN'
  );
}
```

评论选项使用另一套结构特征，不依赖文案：

```text
目标评论行内的可见 button/[role=button]
  └─ 包含 svg[role=img] 或 svg[viewBox="0 0 24 24"]
      └─ 水平三个点/省略号几何子图形，且不是点赞、回复、翻译或表情图标
```

结构匹配只产生候选和评分，不直接保证用途。建议评分项如下：

| 特征 | 作用 |
| --- | --- |
| 位于唯一评论 ID 行内 | 必选，隔离帖子级菜单 |
| 可见、已连接、可聚焦 | 必选 |
| 子级 SVG 有 `aria-label/title` | 加分，不作为唯一条件 |
| SVG 为三个同层圆点或省略号路径 | 加分 |
| 按钮位于评论操作区域右侧 | 加分 |
| `aria-haspopup="dialog"` | 扣分，避免误取帖子头部入口 |
| 标签为点赞、回复、翻译、表情 | 排除 |

只有最高分候选唯一且超过安全阈值时才点击；多个候选并列或没有达到阈值时进入文案降级，仍无法唯一确认则暂停。

### 5.3 第三级：当前状态识别

不读取按钮文案，通过结构判断是否已展开：

- 折叠状态：控件所在父容器没有同级 `ul` 回复容器；
- 展开状态：控件所在父容器出现同级 `ul`，或 `ul` 内出现回复节点；
- 如果存在 `aria-expanded`，优先使用该属性；
- 同一个控件已确认展开后，不重复点击。

### 5.4 点击后结果确认

点击候选控件后保存以下快照：

- 当前可见 `/c/<comment-id>` ID 集合；
- 控件是否仍连接、子节点签名是否改变；
- 父容器是否新增 `ul`；
- 加载指示器状态；
- `MutationObserver` 版本。

点击后只在以下情况之一成立时认定展开成功：

1. 出现新的 `/c/<comment-id>`；
2. 出现同级 `ul` 回复容器；
3. `aria-expanded` 从 `false` 变为 `true`；
4. 控件状态改变且评论面经过稳定等待。

如果只出现输入框、菜单或无关 DOM 变化，则不能认定为回复展开。遇到无法判断的控件，应跳过并记录，正式运行时暂停。

### 5.5 文案匹配的降级职责

文字匹配必须作为结构定位失败后的降级路径，不能与结构候选并行盲点。只用于以下场景：

- Instagram 某个版本移除了上述结构；
- 控件没有可识别的语义属性；
- 结构候选超过一个，需要辅助排序。

文案匹配器应独立成平台标签适配器，统一做 Unicode 归一化、空白归一化、数字和标点归一化以及多语言别名匹配。文案候选的固定优先级为：

1. **日语配置**：`ja`，例如 `コメントのオプション`、`2件すべての返信を見る`、`削除`。
2. **中文配置**：`zh-CN`，例如 `评论选项`、`查看所有2条回复`、`删除`。
3. **其他配置**：`zh-TW`、`en` 以及后续新增语言。
4. **通用兜底**：仅允许完整短语或明确的数字/控件模板，不允许用单个“回复”“更多”“选项”等宽泛词点击。

优先级表示同一批候选中发生冲突时的排序，不表示在中文页面强行先查日语文案；每种语言都应先按当前页面可见标签命中。若不同语言候选同时出现，使用页面 `lang`、`document.documentElement.lang` 和候选所在区域语言推断；无法判断时选择更具体的完整短语，仍并列则暂停。

### 5.6 多语言文案配置文件

新增独立配置文件，例如：

```text
src/content/instagram-control-labels.js
```

配置按控件类型和语言组织，正则只放在配置，不放在扫描流程中：

```js
const INSTAGRAM_CONTROL_LABELS = {
  ja: {
    replyDisclosure: [/^\d+件すべての返信を見る$/, /^返信をすべて見る$/],
    hiddenComments: [/^非表示のコメントを見る$/],
    loadMore: [/^(?:コメント|返信)を(?:さらに|もっと)(?:読み込む|見る)$/],
    commentOptions: [/^コメントのオプション$/, /^オプション$/, /^その他$/],
    delete: [/^削除$/, /^削除する$/, /^コメントを削除(?:する)?$/],
  },
  'zh-CN': {
    replyDisclosure: [/^查看(?:全部|所有)?\s*\d*\s*条回复$/, /^查看所有\d+条回复$/],
    hiddenComments: [/^查看隐藏评论$/],
    loadMore: [/^(?:加载更多|查看更多|查看全部)(?:评论|回复)$/],
    commentOptions: [/^评论选项$/, /^更多选项$/],
    delete: [/^删除$/, /^删除评论$/],
  },
  'zh-TW': {
    delete: [/^刪除$/, /^刪除留言$/],
  },
  en: {
    replyDisclosure: [/^(?:view|see)\s+(?:all\s+)?(?:\d+\s+)?(?:more\s+)?repl(?:y|ies)$/i],
    hiddenComments: [/^(?:see|view)\s+hidden\s+comments?$/i],
    loadMore: [/^(?:load|view|see)\s+(?:more|all)\s+(?:comments?|repl(?:y|ies))$/i],
    commentOptions: [/^(?:comment\s+)?options?$/i, /^more\s+options?$/i],
    delete: [/^delete$/i, /^delete\s+comment$/i],
  },
};
```

实际实现应允许同一语言配置多个模板，以覆盖数字前后空格、全角标点和实验文案。配置加载器需要提供：

```text
getControlLabels(type, languageHints)
matchControlLabel(type, labels, languageHints)
normalizeInstagramLabel(value)
```

定位器先调用结构判断；只有结构候选为空、候选冲突或目标版本缺少稳定语义属性时，才调用 `matchControlLabel()`。新增语言只修改配置和 fixture，不修改点击流程。

### 5.7 删除动作和确认弹层定位

删除动作必须采用“评论行锚定 + 新弹层确认 + 弹层内唯一动作”的链路：

```text
目标评论 ID
  -> 重新定位评论行并校验作者/正文
  -> 悬停并点击该行的评论选项
  -> 保存点击前可见弹层集合
  -> 等待新出现或发生变化的 dialog/menu 弹层
  -> 仅在该弹层内收集删除候选
  -> 唯一候选通过语言配置校验后才允许点击
  -> 等待评论消失或新的删除确认弹层
  -> 如出现确认弹层，再次执行同一删除动作定位
  -> 按评论 ID 消失和评论区稳定确认结果
```

#### 5.7.1 弹层范围

删除动作表面允许的根节点为：

```css
[role="dialog"][aria-modal="true"],
[role="dialog"],
[role="menu"],
[role="listbox"]
```

但不能只按选择器取最后一个节点。点击评论选项前先记录已连接、可见的弹层节点；点击后只接受新连接的节点，或 `aria-expanded`、文本、子节点签名发生明确变化的节点。若仍有多个可疑弹层，必须暂停。

弹层还应满足：

- 可见且已连接；
- 至少包含一个可操作按钮；
- 位于当前标签页最上层的可见交互区域；
- 不属于扩展自己的 Shadow DOM 控制面板；
- 不把帖子顶部“更多选项”或其他页面弹窗作为评论删除弹层。

#### 5.7.2 删除候选

在已确认的弹层内收集：

```css
button,
[role="button"],
[role="menuitem"],
[role="option"]
```

每个候选统一读取自身和子节点的：

```text
可见文本、aria-label、title、SVG aria-label、SVG title
```

候选必须通过以下检查：

1. 可见、已连接、未禁用；
2. 完整标签命中 `delete` 配置；
3. 不包含“举报”“取消”“关闭”等非删除动作；
4. 同一弹层中只有一个删除候选；
5. 如果只有 `举报` + `取消`，记录为权限不足或无删除权限，不得降级点击举报。

#### 5.7.3 删除文案配置

删除配置至少覆盖：

```js
delete: {
  ja: [
    /^削除$/,
    /^削除する$/,
    /^コメントを削除(?:する)?$/,
  ],
  'zh-CN': [/^删除$/, /^删除评论$/],
  'zh-TW': [/^刪除$/, /^刪除留言$/],
  en: [/^delete$/i, /^delete\s+comment$/i],
}
```

优先级仍为日语、简体中文、其他语言；但必须先根据页面 `lang` 和实际可见候选判断语言，不能在中文页面盲目点击隐藏的日文匹配项。单独的“移除”“Remove”等宽泛词只有在对应平台配置明确声明时才能使用。

#### 5.7.4 二次确认和结果确认

第一次删除动作点击后同时等待：

- 目标评论 ID 链接消失；
- 新的确认弹层出现；
- 页面进入明确的错误、权限或验证状态。

如果出现新的确认弹层，必须重新收集该弹层内的删除候选，并再次执行随机等待、唯一候选校验和点击。只有目标评论 ID 消失且评论区完成稳定等待，才增加删除计数。文本消失只能作为评论 ID 无法读取时的兼容回退，并且必须同时校验作者和原始正文。

## 6. 代码调整边界

建议新增两个相互独立但共享基础工具的模块：

```text
src/content/instagram-control-locator.js
src/content/instagram-control-labels.js
```

控件定位模块至少暴露：

```text
findReplyDisclosureControls(root, commentRow)
isReplyDisclosureShape(node)
isExpandedReplyDisclosure(node)
getAccessibleLabels(node)       // 仅作为降级匹配输入
waitForExpansionResult(before)  // ID、ul、aria-expanded、稳定快照
findCommentMenu(commentRow)     // 结构评分优先，文案按 ja -> zh-CN -> 其他降级
captureActionSurfaceState()      // 记录点击前可见弹层，避免复用旧弹层
findActionSurface(beforeState)   // 只接受本次点击新出现或发生变化的弹层
findDeleteAction(surface)        // 仅在已确认的菜单/弹窗内匹配
waitForDeleteResult(commentId)   // ID 消失、二次确认或明确错误
```

文案模块至少暴露：

```text
normalizeInstagramLabel(value)
getLanguageOrder(document, region) // ja -> zh-CN -> 其他
matchConfiguredLabel(type, labels, languageOrder)
```

然后调整：

- `revealCollapsedComments()`：调用统一定位器，不再直接操作正则。
- `ensureReplyDom()`：复用同一定位器，消除扫描/删除前逻辑分叉。
- `comment-pagination-controls.js`：继续允许分页适配器使用标签，但优先使用结构和新增 ID 判断，并调用统一文案配置。
- `rowCommentText()`：优先排除按钮、时间和操作区域节点，而不是维护多语言控件黑名单。
- `commentMenuFor()`：改为 `findCommentMenu()`，只接受评论行内唯一的结构高分候选；找不到时才按日语、中文、其他语言文案降级。
- `visibleDeleteDialog()` / `deleteButtonInDialog()`：改为 `captureActionSurfaceState()`、`findActionSurface()` 和 `findDeleteAction()`，限定在本次评论菜单点击后新出现的弹层内，不从页面正文搜索删除文字。
- `remove()`：拆分“打开评论菜单”“定位第一次删除动作”“处理可选二次确认”“确认评论消失”四个阶段；没有删除权限、弹层不明确或确认失败时暂停。

## 7. 安全要求

- 不匹配 class 名作为唯一依据。
- 不点击评论区内所有 `[role="button"]`。
- 每次最多点击一个候选，点击后等待并重新发现 DOM。
- 元素/结构定位优先；元素找不到才进行文案匹配，文案顺序固定为日语、中文、其他语言。
- 文案匹配必须使用完整短语或明确模板；普通“回复”“更多”“选项”等宽泛词不能单独触发点击。
- 评论选项必须限制在目标评论行内；删除项必须限制在刚打开的可见菜单或弹窗内。
- 删除弹层必须与本次评论选项点击建立新旧状态关系；不能复用页面中原本存在的弹层。
- 弹层只有“举报/取消”时，记录权限不足并暂停或跳过，绝不能把举报当作删除替代动作。
- 第一次删除点击后必须兼容直接消失和出现二次确认两种结果；二次确认仍需唯一删除候选。
- 不把“文案改变”单独作为成功标准，必须结合 `ul`、新评论 ID 或稳定快照。
- 无法确认控件用途时暂停，并在面板中显示“发现未识别的回复展开控件”。
- Preview 可以记录候选结构和点击结果；正式运行仍必须保持回复优先、作者保护、白名单和删除前重新定位。

## 8. 测试计划

### 单元测试

新增结构化 DOM fixture，至少覆盖：

1. 中文 `查看所有2条回复`；
2. 日文 `2件すべての返信を見る`；
3. 英文任意回复展开文案；
4. 随机字符串但结构完全相同，确认仍能被识别；
5. 普通“回复”按钮，确认不会被识别；
6. 已有同级 `ul` 的展开状态，确认不会重复点击；
7. 空 div class 改变，确认结构定位仍然有效。
8. 中文评论选项标签位于子级 SVG `aria-label/title`，确认递归标签读取有效。
9. 日文评论选项、中文评论选项、英文评论选项同时存在时，确认候选排序按配置和页面语言工作。
10. 评论行外的帖子“更多选项”带 `aria-haspopup="dialog"`，确认不会被评论菜单定位器选中。
11. 元素结构缺失时，确认按日语文案、中文文案、其他语言文案依次降级。
12. 删除弹窗外出现“删除”文本，确认不会被误识别；只有弹窗内删除操作可被选中。
13. 自有评论菜单的普通 `<button>删除</button>` 能被识别，即使没有 `role`、`aria-label` 或 `title`。
14. `コメントを削除`、`コメントを削除する`、`删除评论`、`刪除留言` 均能命中对应语言配置。
15. 他人评论菜单只有 `举报`、`取消` 时，确认报告为权限不足，不会点击举报。
16. 点击前已有其他 dialog 时，确认删除定位器只接受本次评论菜单新出现的弹层。
17. 第一次删除点击后直接消失和出现二次确认弹窗两种流程均能正确处理。

### 浏览器验证

在中文、日文和英文页面分别使用 Preview：

- 记录展开控件数量；
- 记录点击前后 `/c/<comment-id>` 集合；
- 记录 `ul` 是否出现；
- 确认未点击普通“回复”、点赞或菜单按钮；
- 确认页面刷新后仍能重新发现控件。
- 在中文页面移除结构标签后，确认文案配置仍能按预定顺序找到控件；恢复结构后确认优先回到元素定位。
- 在自有作品 `DcSPgoiJhLn` 上使用 Preview 记录评论选项弹层中的动作，不点击删除；正式删除只使用测试账号和临时评论小批量验证。

静态测试通过不能替代真实 Instagram 验证。正式删除前仍需使用测试账号和少量临时评论进行 Preview 与小批量删除验证。

## 9. 验收标准

满足以下条件才可替换现有正则主路径：

1. 中文页面的 `查看所有N条回复` 优先通过结构识别，不依赖文案；结构缺失时能命中中文配置。
2. 日文、英文和未知字符串的同结构控件均可识别。
3. 评论选项按钮优先通过评论行内结构识别；找不到元素时按日语、中文、其他语言文案降级。
4. 普通“回复”按钮、点赞按钮、帖子更多菜单不会被误点。
5. 展开后出现 `ul` 或新的评论 ID 时，扫描能够继续；未出现有效变化时会暂停或跳过。
6. 删除项只从当前可见菜单/弹窗定位，删除文案按统一配置匹配。
7. 他人评论没有删除权限时不会误点举报；自有评论的普通 `button` 删除项可以识别。
8. 删除后直接消失和二次确认弹窗两种流程都能确认目标评论 ID 消失。
9. `revealCollapsedComments()` 与 `ensureReplyDom()` 使用同一套定位逻辑。
10. `npm test`、`node --check` 和 `git diff --check` 全部通过，并完成真实浏览器 Preview 记录。
