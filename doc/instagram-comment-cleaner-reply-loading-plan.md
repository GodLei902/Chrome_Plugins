# Instagram 评论清理器：一级评论子级加载优化方案

> （已废弃）此文描述的接口响应监听方案已移除。当前实现改为纯 DOM 评论采集，详见 [instagram-comment-dom-only-plan.md](./instagram-comment-dom-only-plan.md)。

## 方案摘要

当前 Instagram 页面中的评论分为两层数据：评论主列表返回一级评论，点击一级评论的回复入口后，Instagram 再通过独立接口返回子级评论。现有脚本只从页面 `script[type="application/json"]` 读取主列表数据，因此页面上已经显示的子级回复可能没有进入扫描树，也就无法进入候选。

本方案只处理“当前评论容器中已经加载的一级评论及其首次子级回复”：

- 页面加载时由 `document_start`/MAIN world 监听器旁路观察 Instagram 自己发出的评论响应。
- 每次点击“开始”或“预览”时，先从响应缓存读取全部一级评论；对 `child_comment_count > 0` 的一级评论自动点击回复入口，由页面自身触发首次子级请求。
- 扩展只解析被动收到的响应，不构造或发送 GraphQL 请求；收到完整响应后再合并评论树并执行候选筛选。
- 当前不自动滚动、不自动加载一级评论分页，也不请求子级游标分页。
- 用户手动加载下一批一级评论后，再点击“开始”，脚本重新扫描当前容器并继续处理。

抓取目录中的报文只用于确认接口字段和响应结构，不作为固定数据 fixture 写入运行逻辑；实现不得依赖示例中的 5 条一级评论、两个父评论或固定评论 ID。

## 当前数据事实

### 一级评论主列表

主列表接口返回路径：

```text
data.xdt_api__v1__media__media_id__comments__connection.edges[].node
```

运行时需要从节点读取：

- `pk`：评论 ID
- `user.username`：作者
- `text`：文本
- `parent_comment_id`：一级评论通常为 `null`
- `child_comment_count`：子级数量提示
- `__typename`：必须为 `XDTCommentDict`

### 首次子级响应

首次子级接口响应路径：

```text
data.xdt_api__v1__media__media_id__comments__parent_comment_id__child_comments__connection.edges[].node
```

接口操作参数和变量形状以抓取记录为参考：

- `doc_id=27823744063932558`
- `variables.media_id=<运行时媒体 ID>`
- `variables.parent_comment_id=<运行时一级评论 ID>`
- `variables.__relay_internal__pv__PolarisIsLoggedInrelayprovider=true`

这些字段只用于解析和诊断；监听器不复制变量、不重放请求，避免扩展额外制造接口流量。

## 实现改动

### 1. 动态构建评论树

在 `src/content/social-comment-cleaner.js` 中拆分现有 `threads()` 流程：

1. 从响应监听器收到任意数量的一级 `XDTCommentDict`，按 `pk` 去重。
2. 对 `child_comment_count > 0` 的一级评论查找并点击“查看回复”入口，等待对应 `parent_comment_id` 的被动响应。
3. 将响应节点归一化并写入同一个评论 Map。
4. 根据 `parent_comment_id` 建立 `thread.replies`，再交给规则引擎。

建议新增内部方法：

- `expandChildReplies(threads)`
- `waitForParentResponse(parentCommentId)`

`threads()` 和 `scan()` 需要改为异步，以保证子级数据合并完成后才执行候选筛选。

### 2. 子级加载缓存与后续分页留口

缓存以一级评论 ID 为键，缓存内容至少包括：

- 已归一化的子级评论数组
- `hasNextPage`
- `endCursor`
- 加载状态和错误信息

当前版本只接受页面点击触发的首次子级响应。若返回 `hasNextPage=true`，保存游标并标记为 `partial`，不由扩展补发分页请求。

同一页面会话中已收到完整响应的父评论不重复点击；用户手动加载更多一级评论后点击“开始”，只对新出现或尚未完成的父评论补充点击。

### 3. 候选和删除定位

现有规则保持不变：

- 一级评论永远不会成为删除候选。
- 帖子作者评论和白名单评论优先跳过。
- 命中删除关键词的子级回复进入候选。
- 先处理子级回复，再考虑后续扩展。

`locateCommentElement(candidate)` 调整为：

1. 优先查找 `/p/<shortcode>/c/<comment_id>/` 链接对应的评论块。
2. 对定位结果校验作者和文本。
3. ID 链接不可用时，回退到现有作者 + 文本匹配。

删除确认优先验证目标评论 ID 对应节点已消失，再以文本消失作为兼容性回退，避免同文本评论误判。

### 4. 失败和完成状态

某个一级评论的子级响应超时、结构异常或返回节点的父 ID 不匹配时：

- 不合并该父评论的部分结果。
- 只跳过该一级评论下的子级。
- 继续处理其他已成功加载的一级评论。
- 在面板中累计子级加载失败数量，并保留父评论 ID/文本摘要用于诊断。

任务结束时不能笼统显示“全部评论已处理”，需要区分：

- 当前容器中已确认的子级已处理完成。
- 存在子级加载失败的一级评论。
- 存在 `hasNextPage=true` 但暂未请求的子级分页。

## 用户手动翻页后的运行语义

本版本不自动滚动、不自动点击“查看更多一级评论”，也不自动请求一级评论主列表分页。

预期流程：

1. 用户在 Instagram 中加载当前一级评论批次。
2. 点击“开始”或“预览”，脚本从响应缓存读取一级评论，自动点击回复入口并等待页面响应。
3. 当前容器没有待处理候选时，脚本停止本轮任务。
4. 用户手动加载下一批一级评论。
5. 用户再次点击“开始”，脚本重新读取当前容器，发现新一级评论并加载其子级。

已删除或已不存在的评论不会因重新扫描再次进入候选；候选去重继续使用评论 ID。

## 测试与验收

### 单元和静态测试

- 用抓取报文构造通用 fixture，验证监听器可提取任意数量一级评论和子级评论并按父 ID 建树。
- 验证多个一级评论、重复一级评论、无子级评论、单父评论多个子级评论。
- 验证 `child_comment_count=0` 不点击子级入口。
- 验证同一父评论在重扫时不重复点击已完成响应。
- 验证 `has_next_page=true` 只记录游标，不触发分页请求。
- 验证单个父评论失败不会阻断其他父评论。
- 运行 `node --check`、`node --test test/*.test.js`、`git diff --check`。

### 浏览器验收

1. 在目标帖子加载第一页一级评论，预览时确认已加载回复数包含当前批次所有可获得子级。
2. 确认示例中的两条子级可被识别为子级数据，而不是一级评论。
3. 使用测试账号执行删除，确认通过评论 ID 定位并逐条确认删除。
4. 删除完成后用户手动加载下一批一级评论，再点击“开始”。
5. 确认新一级评论及其子级可以继续被发现、筛选和删除。
6. 确认实现不依赖固定评论数量、固定父评论 ID 或固定文本。

## 本次明确不实现

- 一级评论自动分页、自动滚动和自动点击加载。
- 扩展主动请求子级接口或补发子级回复游标分页。
- 绕过登录、权限、验证码或 Instagram 风控机制。
- 将 DOM 文本扫描作为评论身份主数据源。
