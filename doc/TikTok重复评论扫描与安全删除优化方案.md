# TikTok 重复评论扫描与安全删除优化方案

## 1. 背景与结论

在 TikTok 同一一级评论线程内，允许同一账号连续发表多条正文完全相同的回复。这是正常页面数据，不应仅因作者、正文和父级相同而中止整轮扫描。

当前实现把“作品、层级、父级、作者和正文摘要”拼接为 `CommentRecord.id`。当两条真实回复的这些字段一致时，`comments.collect()` 会把它们视为稳定键冲突并返回 `ambiguous`，核心因此暂停。现有 `id` 同时承担了三种不应混用的职责：

1. 当前评论面中每条记录的实例标识；
2. 分页和扫描统计的去重键；
3. 跨刷新会话的 `processedIds` 删除去重键。

本方案将这三类职责分离。目标行为是：**重复评论可以继续扫描；当前稳定页面内可以逐条安全处理；刷新或重绘后无法唯一确认时，只暂停受影响的重复组，不猜测删除，也不阻塞其他评论。**

## 2. 适用范围与非目标

本方案仅调整 TikTok 插件与通用核心对“同父级、同账号、同正文”的重复回复的处理方式。

不改变以下行为：

- Preview 只扫描、筛选和统计，绝不打开菜单或删除评论。
- 一级评论仍默认保护，不进入删除候选。
- 内容作者、白名单和关键词规则仍由 `core/candidate-policy.js` 统一处理。
- 多个评论面、多个菜单、多个删除按钮、父级无法唯一映射、挑战、限流和未知页面状态仍立即暂停。
- 不调用 TikTok 私有接口，不把 DOM 节点、菜单文本、账号名称或页面私有数据持久化。
- 不以点赞数、相对时间或 DOM 顺序作为跨刷新永久身份。

## 3. 现状问题

当前 TikTok 稳定键的组成如下：

```text
contentId + kind + parentId + normalizedUsername + digest(text)
```

它适合作为“语义相同评论”的分组依据，却不足以识别两条真实的相同回复。当前代码在 `src/platform/tiktok/comments.js` 收集记录时发现相同 `id` 就停止；`src/platform/tiktok/actions.js` 在动作前也要求该键全页唯一；删除验证还要求相同键完全消失。

因此，单纯放宽 `collect()` 的重复检查并不安全：

- 删除第一条后，第二条仍具有相同语义键，旧验证会错误地认为删除失败；
- 若用组内序号扩展 `id`，删除第一条后其余评论可能重新编号，旧 `processedIds` 会跳过尚未删除的评论；
- 刷新、虚拟列表回收或节点重绘后，旧 DOM 顺序不一定能够可靠复现。

## 4. 设计原则

1. **语义相同不等于同一实例。** 重复语义键是可处理的数据状态，不是扫描级异常。
2. **当前页面身份与跨刷新身份分离。** 当前稳定 DOM 中可使用短期实例键；会话持久化只使用可跨刷新复现的真实平台 ID。
3. **删除前后均验证。** 删除前必须唯一定位具体行；删除后必须确认目标行消失或所在重复组数量恰好减少一条。
4. **碰撞局部化。** 无法安全处理的重复组暂停该组，不影响其他唯一评论和其他线程的扫描。
5. **不依赖易变字段恢复。** 时间、点赞数、组内顺序只可作为当前页面内的辅助动作证据，不能写入 `processedIds`。

## 5. 数据模型

保留 `CommentRecord.id` 作为当前扫描实例键，并在 `CommentRecord.platform` 中保留 TikTok 私有的分组与定位信息。核心只读取统一字段和插件明确提供的去重键，不解释 `platform` 内部字段。

```js
{
  id: '当前扫描实例键',
  parentId: '父评论实例键',
  kind: 'reply',
  username: 'author',
  text: 'comment text',
  isPostAuthor: false,
  element: null,
  platform: {
    semanticKey: '作品+层级+父级语义键+作者+正文摘要',
    scanKey: 'semanticKey#occurrence-2',
    collision: true,
    collisionGroupSize: 2,
    occurrence: 2,
    persistentKey: '',
    locator: {
      authorHref: '/@author',
      relativeTime: '页面内辅助证据',
      likes: '页面内辅助证据',
      previousSibling: '页面内辅助证据',
      nextSibling: '页面内辅助证据'
    }
  }
}
```

字段含义如下：

| 字段 | 作用 | 可持久化 |
| --- | --- | --- |
| `semanticKey` | 归并同一语义的评论，用于碰撞分组 | 否，除非平台存在真实评论 ID |
| `scanKey` / `id` | 当前稳定评论面的一条具体实例 | 否 |
| `persistentKey` | 跨刷新识别已验证删除的评论 | 仅平台真实 ID 时允许 |
| `locator` | 当前页面重新定位行的辅助证据 | 否 |

`CommentRecord.platform` 的内容不进入长期会话存储；保存检查点时必须通过 `CommentRecord` 的序列化逻辑剥离短期定位信息。

## 6. 插件改造

### 6.1 解析与收集

调整 `src/platform/tiktok/comments.js`：

1. 先为所有行生成 `semanticKey`，不因重复立即返回错误。
2. 按 `semanticKey` 分组并按当前 DOM 中的同组顺序分配 `occurrence`。
3. 生成当前扫描专用的 `scanKey`，例如 `semanticKey#occurrence-1` 和 `semanticKey#occurrence-2`。
4. 将 `scanKey` 作为本轮 `record.id`，并把碰撞信息保留在 `record.platform`。
5. 仅在作者、正文、父级、评论行或评论面本身无法可靠解析时返回 `ambiguous`。

同组顺序仅描述当前稳定 DOM，不得被当作刷新后的身份依据。

### 6.2 短期定位

调整 `src/platform/tiktok/actions.js` 的 `resolveElement()`：

1. 若 `record.element` 仍连接在 DOM 中，并且父级、作者链接、正文、层级及当前行结构仍匹配，优先复用此元素。
2. 元素已重绘时，先按 `semanticKey` 找到候选组，再结合当前页面内的辅助证据筛选：父级、作者链接、正文、相对时间、点赞数、相邻行摘要和 `occurrence`。
3. 只有结果唯一时才返回元素；零条、两条以上或辅助证据相互矛盾时返回 `ambiguous`。
4. 点赞数、相对时间、相邻行和组内顺序只能参与当前页面一次动作，不能写入长期会话或作为恢复依据。

### 6.3 删除验证

调整 `verifyDeleted()`：

- 非碰撞评论：保持现有语义键完全消失的验证逻辑。
- 碰撞组：动作前记录该组数量 `N`；删除后等待评论面稳定，并要求同组数量严格变为 `N - 1`。
- 同时要求原目标元素断开，或删除后重新定位时不再能以相同短期定位证据识别该实例。
- 组数量不变、减少超过一条、评论面在验证窗口发生无法解释的加载或重绘时，返回 `ambiguous`。

删除验证成功前不得更新 `deleted`、`processedIds` 或继续下一个候选。

## 7. 核心改造

### 7.1 扩展评论契约

在 `PlatformPlugin.comments` 中增加以下可选且有默认降级实现的方法：

```js
getScanKey(record)        // 当前扫描实例键，默认 record.id
getPersistentKey(record)  // 可跨刷新身份；无法确认时返回空字符串
getCollisionGroup(record) // 当前页面重复组标识；非碰撞时返回空字符串
isResumable(record)       // 是否可安全跨刷新继续处理
```

为了不影响现有 Instagram 插件，默认实现应为：

```js
getScanKey: (record) => String(record?.id || ''),
getPersistentKey: (record) => String(record?.id || ''),
getCollisionGroup: () => '',
isResumable: () => true,
```

TikTok 对无真实评论 ID 的碰撞记录返回空 `persistentKey` 和 `false`。

### 7.2 键的使用边界

核心中使用 `record.id` 的位置需要按目的替换：

| 目的 | 使用的键 |
| --- | --- |
| 当轮扫描统计、候选队列、Preview 展示 | `getScanKey(record)` |
| 会话 `seenIds`、`matchedIds`、`skippedIds` | `getScanKey(record)` |
| `processedIds`、刷新恢复与跨轮跳过 | `getPersistentKey(record)`，为空时不写入 |
| 重复组调度 | `getCollisionGroup(record)` |

核心不得读取 TikTok 的 `platform.locator`、`occurrence` 或其他平台私有字段。

### 7.3 碰撞组调度

修改 `CleanerRuntime` 的候选处理流程：

1. 唯一候选维持现有串行逻辑。
2. 对同一 `collisionGroup`，一次仅取一个当前页面候选执行。
3. 删除验证成功后，重新稳定评论面并重新扫描该父线程。
4. 根据新的当前页面记录重新选择该组下一条候选，不能复用旧的 `occurrence` 或旧候选对象。
5. 当前轮中已经安全确认删除的碰撞实例应只保留在内存中的短期处理集合，避免同一稳定页面重复执行。
6. 页面刷新、会话恢复或评论面更换后清空该短期集合；没有 `persistentKey` 的碰撞评论不自动续删。

若碰撞组中的一条无法重新定位，暂停并显示该组原因；其他未受影响的线程仍可继续扫描。若当前核心会话模型只能全局暂停，则第一阶段先将碰撞组标记为“待人工确认并跳过”，完成局部错误隔离后再开放同页自动处理。

### 7.4 会话与检查点

`TaskSession.addProcessed()` 需要接收持久化键，而不是默认读取 `record.id`。建议增加显式参数：

```js
addProcessed(record, persistentKey)
```

行为：

- `persistentKey` 非空：写入 `processedIds`，删除数加一。
- `persistentKey` 为空但删除已验证：删除数仍加一，但不写入 `processedIds`；当前轮使用短期集合防重。
- 下一次刷新或恢复后，不根据旧 `scanKey`、`occurrence`、时间或点赞数自动跳过或删除。

检查点仅保存统一统计、真实 `processedIds` 和可序列化的通用会话状态，不保存 DOM 节点、定位证据、账号名、正文或顺序。

## 8. UI 文案

将现有扫描级错误改为区分状态：

| 场景 | 建议文案 |
| --- | --- |
| Preview 发现重复语义评论 | `已发现内容重复的评论，继续扫描。` |
| 当前页面可安全逐条处理 | `发现重复评论组，将在当前页面逐条验证处理。` |
| 刷新后不可恢复 | `部分重复评论缺少可跨刷新确认的身份，刷新后不会自动续删。` |
| 当前页面无法区分某一组 | `一组重复评论无法唯一定位，已跳过该组并继续扫描其他评论。` |
| 菜单、确认或验证不明确 | 保持现有暂停文案与安全语义 |

面板统计应分开显示“扫描到的重复实例数”“本轮已验证删除数”“因无法唯一定位而跳过的实例数”，但不展示账号名、正文、DOM 属性或定位证据。

## 9. 分阶段实施

### 阶段 1：扫描与 Preview 解耦

- 在 TikTok 解析器中引入 `semanticKey`、`scanKey` 和碰撞组标记。
- `collect()` 遇到重复语义键时返回多条实例记录，不再暂停。
- 核心统计、Preview 候选和分页新增统计改为使用扫描实例键。
- 正式执行暂时跳过无持久化身份的碰撞组，继续处理非碰撞候选。
- 该阶段不改变现有删除动作和 `processedIds` 语义。

验收：重复评论不阻断 Preview 和扫描；没有重复的评论行为不变；碰撞评论不会被自动删除。

### 阶段 2：当前页面内逐条删除

- 实现元素优先与短期辅助证据的两级定位。
- 为碰撞组实现“删除前后组数量减少一条”的验证。
- 核心每成功删除一条后重新扫描当前父线程，不复用旧序号。
- 引入内存短期防重集合，防止同页重复删除。

验收：同页两条相同回复可顺序删除；删除第一条后第二条不会跳过；无法唯一定位时只跳过该组或按当期局部错误模型暂停。

### 阶段 3：恢复与局部错误隔离

- 增加插件契约的扫描键、持久化键和碰撞组方法。
- 将 `TaskSession` 与 `CleanerRuntime` 的处理键显式分离。
- 实现碰撞组局部跳过和 UI 统计。
- 验证刷新、暂停、恢复与计划续跑不会依据旧顺序删除重复评论。

验收：有真实 ID 的记录跨刷新不重复处理；无真实 ID 的碰撞组不自动续删；其他线程和唯一评论不受碰撞组影响。

## 10. 测试清单

### 插件解析测试

- 同父级、同账号、同正文的两条回复返回两条记录。
- 两条记录的 `semanticKey` 相同，`scanKey` 不同。
- 碰撞组大小、实例序号和短期定位信息符合预期。
- 作者、正文、父级或评论行证据不唯一时仍返回 `ambiguous`。

### Preview 与核心测试

- 重复实例全部计入扫描数和关键词命中数。
- Preview 不打开菜单、不点击删除、不写入 `processedIds`。
- 非碰撞候选可在重复组存在时继续进入候选队列。
- 相同正文的两条候选不会被 `Map` 或 `Set` 错误合并。

### 删除与验证测试

- 当前元素仍连接时优先用元素引用定位。
- 节点重绘后，短期证据唯一时能重新定位。
- 两条重复评论中删除第一条后，同组数量由 2 变 1 才算成功。
- 删除后数量不变、减少超过一条、菜单重复、确认弹层重复或定位不唯一时失败且不更新删除数。
- 删除第一条后，重新扫描产生的新序号不会让第二条被错误跳过。

### 恢复测试

- 具有真实平台 ID 的记录仍使用 `processedIds` 跨刷新防重。
- 无真实 ID 的重复组不写入普通 `processedIds`。
- 暂停、刷新和恢复后不会仅凭旧 `occurrence`、点赞数或相对时间继续删除。
- 重新加载页面后，其他唯一候选仍可正常恢复。

## 11. 真实页面验收边界

仅在测试账号、可管理作品和小批量条件下验证。验收记录只保存页面类型、测试批量、重复组数量、Preview 结果、删除验证结果和暂停原因，不记录账号名、评论正文、菜单文本或 DOM 快照。

至少覆盖：

1. 同一账号在同一父评论下发布两条相同回复；
2. 同一页面中逐条删除并验证两次组数量变化；
3. 删除第一条后的重绘与第二条重新定位；
4. 删除前刷新、删除后刷新及暂停恢复；
5. 无法唯一定位时跳过或暂停的安全行为；
6. 普通唯一回复、一级评论保护、白名单和内容作者保护的回归。

在未完成真实页面验收前，不得宣称已证明真实 TikTok 删除成功。

## 12. 完成定义

完成本方案需同时满足：

- 同账号同父级同正文的重复回复不再导致全局扫描暂停；
- Preview 可完整统计重复实例且无页面动作；
- 当前稳定页面中，重复实例仅在可唯一定位与可验证删除时逐条处理；
- 删除计数只在插件明确验证成功后增加；
- 无真实平台 ID 的碰撞实例不会通过顺序、时间或点赞数跨刷新自动续删；
- `core/` 不包含 TikTok DOM、选择器、页面文案或平台私有字段解释；
- 修改文件通过 `node --check`、`npm test` 与 `git diff --check`，并完成小批量真实页面验收记录。
