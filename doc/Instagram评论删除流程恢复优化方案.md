# Instagram 评论删除流程恢复优化方案

## 1. 目的与不可变约束

本方案用于将当前项目中的 Instagram 评论删除流程恢复到
`/Users/gaodalei/Desktop/评论清理器V2.0.0正式版`（下称“旧版”）的行为。

旧版是本次工作的唯一真值。恢复完成的定义不是“当前实现更严格、更模块化或测试更多”，而是用户在页面上可观察到的流程、判断、顺序、状态和结果均与旧版一致。

以下约束不可突破：

1. 旧版目录只读：不得修改、格式化、复制覆盖、生成文件或在其中运行会写入文件的命令。
2. 后续只允许修改当前仓库；旧版仅用于阅读、建立基线和回归比对。
3. 不得借“优化”改变旧版的删除条件、页面动作顺序、等待窗口、状态转移、输入解释或停止条件。
4. 当前的插件化、`WaitCoordinator`、统一节奏和测试结构只可作为适配外壳；它们不能改变旧版流程的可观察行为。
5. 未在测试账号和小批量真实页面完成验证前，不得宣称真实 Instagram 删除已验收。

本文件是实施设计和验收依据，不包含代码修改。

## 3. 旧版行为基线

### 3.1 启动与保护

1. 设置页读取 `targetPostUrl`、白名单、关键词和节奏配置。
2. 以设置中保存的 `targetPostUrl` 作为任务目标，并校验当前页面与该目标一致；不得以当前页面静默覆盖配置目标。
3. 获取该 Instagram 目标的任务锁，并以 30 秒周期续租。
4. 等待评论面处于稳定状态，无法确认时不进入删除。
5. 正式运行沿用旧版的前置确认、检查点和锁语义；Preview 仅扫描、筛选、统计，不打开菜单、不点击删除。

### 3.2 扫描、展开与候选构建

1. 以一级评论为单位遍历。
2. 对当前一级评论展开其回复，而非先对整页所有一级评论统一展开。
3. 解析当前稳定评论面，建立父子评论树。
4. 只把回复列为删除候选；一级评论始终不删除。
5. 先保护帖子作者评论和白名单作者，再应用关键词规则。
6. 正式删除一条回复后，重新展开该回复所属一级评论并重新扫描，避免页面重绘或新加载内容导致误判。

### 3.3 单条删除

对每个候选回复，旧版按以下顺序处理：

1. 重新定位评论元素；找不到唯一元素即中止危险动作。
2. 将元素滚动到可操作视口并悬停。
3. 等待最多 1.8 秒让评论菜单出现。
4. 经统一节奏和全局限频协调后打开菜单。
5. 使用旧版菜单定位规则找到唯一的删除项；不明确时不删除。
6. 点击删除；若页面出现二次确认，按旧版规则最多再确认两次。
7. 以目标评论 ID 或正文在可见评论面中消失作为删除成功信号。
8. 成功信号出现后，继续等待评论面达到删除后的稳定状态。
9. 只有上述确认均成功，才增加删除数、记录 `processedIds` 并保存检查点；否则暂停或失败，不得跳过并继续。

### 3.4 批次、分页与续跑

1. 连续删除达到配置上限后，先重新扫描当前评论面；再进入休息，休息后继续。
2. 当前批次处理后继续加载下一页评论。
3. 仅在分页已完成且本轮未获得任何新评论 ID（`completed && !newIds`）时结束；即使页面已显示末页，只要还有新增 ID 仍要处理。
4. 正式运行结束后进入 10 至 60 分钟的自动刷新续跑窗口。
5. 旧版支持从 `running`、`scheduled-rest`、`refreshing` 状态恢复。
6. Pause 保存检查点并释放锁；Stop 清理会话并回到 `idle`。

## 4. 已识别差异与恢复决策

下表是静态代码核对得到的差异。每一项均以旧版为准；“恢复决策”是后续实现的验收口径。

| 编号 | 当前实现的差异 | 旧版基线 | 恢复决策 |
| --- | --- | --- | --- |
| D01 | 面板启动路径可能将配置目标替换为当前页面 URL。 | 严格使用已配置的 `targetPostUrl`，并要求当前页与目标匹配。 | 恢复“配置目标为唯一真值”，当前页面只用于校验。 |
| D02 | 新增的正式运行 preflight 可能改变旧版删除前的判断顺序或暂停时点。 | 旧版按既有启动、锁、稳定面和会话流程进入处理。 | 保留安全检查，但以适配方式嵌入；外部时序、可恢复状态和删除准入必须与旧版一致。 |
| D03 | 回复展开偏向先整面展开。 | 逐个一级评论展开回复。 | 恢复逐父评论展开；删除后只重新展开当前父评论并重扫。 |
| D04 | 菜单动作未完整保留 `scrollIntoView()` 与最多 1.8 秒的菜单等待。 | 重定位、滚动、悬停、等待菜单后再操作。 | 原样恢复这四个阶段及失败分支。 |
| D05 | 当前定位策略比旧版严格，可能丢失旧版可删除的兼容页面形态。 | 使用旧版定位和兼容回退规则，但菜单项必须唯一。 | 将旧版定位规则完整封装为插件适配层；保留“不唯一即暂停”。 |
| D06 | 删除确认后的可见性判断与旧版不同，且缺少显式的删除后稳定等待。 | 评论 ID/正文消失后继续等待评论面稳定。 | 恢复旧版成功信号与稳定等待；成功前不得写 `processedIds` 或累计删除数。 |
| D07 | 达到连续删除上限时，休息与重扫的先后可能相反。 | 先重扫，后休息。 | 恢复旧版顺序，防止休息前丢失页面变化。 |
| D08 | 分页在 `completed + newIds` 场景可能提前退出。 | 只有 `completed && !newIds` 才结束。 | 恢复精确结束条件，末页新增评论必须进入候选处理。 |
| D09 | SPA 导航时的停止语义与旧版不同。 | 旧版在相应页面变化下按既有停止/清理规则处理。 | 以旧版触发条件、清理顺序和用户可见状态为准。 |
| D10 | Stop 后的终态可能保留为 `stopped`。 | Stop 清理会话并回到 `idle`。 | 恢复 `idle` 终态和旧版 UI 快照。 |
| D11 | 当前续跑/恢复覆盖范围与旧版不同。 | 支持 `running`、`scheduled-rest`、`refreshing`。 | 恢复三类状态的检查点、锁和续跑语义。 |
| D12 | 白名单、关键词支持逗号分隔。 | 旧版仅按换行解释输入。 | 恢复换行分隔语义；不得静默扩大匹配规则。 |
| D13 | `WaitCoordinator` 的接入可能使分页、稳定采样或超时行为与旧版不同。 | 旧版的加载、稳定和超时决定何时继续、暂停或结束。 | 只替换内部等待实现，保留旧版触发条件、窗口和结果；取消必须额外满足现有安全约束。 |
| D14 | 当前会话/插件边界可能将旧版的检查点、锁、统计更新移动到不同时点。 | 删除验证成功后才更新统计与检查点，Pause/Stop 有固定释放顺序。 | 以旧版时点为准；插件只回报明确结果，核心在对应旧版时点更新会话。 |

## 5. 恢复设计原则

### 5.1 行为等价优先

必须先使每一个旧版分支可追踪，再考虑内部重构。下面的变化都属于不允许的“优化”：

- 把逐父评论展开改成批量展开；
- 缩短、延长、取消或合并旧版菜单等待、删除确认和稳定等待；
- 改变重扫、休息、分页、检查点写入的顺序；
- 把旧版暂停改成忽略、跳过、重试或直接完成；
- 扩展目标 URL、白名单、关键词的输入解释；
- 用更严格的定位规则替换旧版仍支持的页面形态；
- 因为核心/插件划分而改变 UI 终态或恢复范围。

### 5.2 允许的内部优化边界

以下优化仅在行为回归测试证明等价后允许进行：

- 以 `WaitCoordinator` 统一可取消等待和 Mutation 订阅；
- 以 Instagram 插件封装选择器、DOM 定位、菜单操作和页面错误分类；
- 以 `TaskSession` 持久化锁、检查点、统计和 UI 快照；
- 增加日志、埋点、测试桩和诊断信息，但不得暴露或改变用户操作；
- 在当前核心/共享模块中复用节奏、限频和取消能力，但实际操作节点和等待窗口仍遵循旧版。

## 6. 分阶段恢复计划

每阶段都应单独提交、可回滚，并且在进入下一阶段前完成该阶段的静态检查与单元测试。不得同时实施不相干的架构改造。

### 阶段 0：冻结基线与建立对照

- 为旧版涉及的文件生成只读哈希清单，保存到当前仓库的恢复记录中；清单仅用于验证旧版未被触碰。
- 为本文件第 3 节每一个步骤建立“旧版证据位置—当前职责—测试用例”追踪表。
- 保留当前工作区已有的未提交修改，不覆盖、不重置、不混入恢复提交。

验收：旧版工作树无变化；当前工作树中除明确新建的文档、测试或恢复代码外无关联改动。

### 阶段 1：目标 URL、设置与启动恢复

涉及：`src/options/options.js`、`src/options/platform-form.js`、`src/background/routing.js`、`src/core/cleaner-runtime.js`。

- 恢复配置目标 URL 的保存、标准化和当前页一致性校验。
- 恢复白名单和关键词的旧版换行输入语义。
- 对照旧版恢复启动、锁获取、30 秒续租、检查点加载及初始状态。
- 若保留新的 preflight，把它放进等价节点：任何新增 `unknown`、`ambiguous` 等结果都必须转换为与旧版相同的暂停/错误可见状态，不能绕过或提前改变流程。

验收：错误目标 URL、当前页不匹配、未登录、无删除权限、Preview、Start 均有与旧版一致的状态和不变性。

### 阶段 2：评论面、展开和候选恢复

涉及：`src/core/cleaner-runtime.js`、`src/platform/instagram/surface.js`、`src/platform/instagram/loader.js`、`src/platform/instagram/parser.js`、候选规则模块。

- 恢复“遍历一个一级评论 → 展开其回复 → 建树与筛选”的循环。
- 恢复只删除回复和一级评论绝不进入候选队列的规则。
- 恢复作者保护、白名单保护优先于关键词匹配的顺序。
- 删除后按旧版重新展开对应父评论并重新扫描。
- 使用观察器和可取消等待实现稳定面，但等价保留旧版的稳定判定和超时结果。

验收：模拟多父评论、多层回复、懒加载、页面重绘、保护作者和关键词交叉条件；候选顺序及数量与旧版对照结果一致。

### 阶段 3：单条删除动作恢复

涉及：`src/platform/instagram/actions.js`、`src/platform/instagram/control-locator.js`、`src/core/cleaner-runtime.js`。

- 复原重新定位、滚入视口、悬停、最多 1.8 秒菜单等待、节奏协调、菜单打开、唯一删除项定位、最多两次二次确认的顺序。
- 用旧版定位规则及其回退覆盖兼容页面；只有定位结果不唯一时暂停。
- 恢复“评论 ID 或正文从可见评论面消失”这一确认方式，随后再等待删除后稳定。
- 确保任何步骤的元素失效、菜单歧义、确认失败、稳定等待失败都不产生统计和检查点副作用。

验收：菜单迟到、菜单不存在、多个删除项、二次确认 0/1/2 次、DOM 重绘、正文相同但 ID 不同、删除后稳定超时等测试均有明确结果。

### 阶段 4：限额、休息、分页和自动续跑恢复

涉及：`src/core/cleaner-runtime.js`、`src/platform/instagram/loader.js`、共享节奏/限频模块、后台会话存储。

- 恢复“达到连续上限后先重扫、再休息”的顺序。
- 恢复 `completed && !newIds` 的唯一结束条件。
- 恢复正式运行完成后的 10 至 60 分钟刷新续跑窗口及其调度。
- 所有刷新、分页、滚动动作使用统一可取消协调器，但不能改变旧版应等待/继续/结束的判断。

验收：末页有新增 ID、末页无新增 ID、达到限额、休息后恢复、刷新时出现新回复、刷新无新回复。

### 阶段 5：Pause、Stop、恢复和导航恢复

涉及：`src/core/task-session.js`、`src/core/cleaner-runtime.js`、`src/background/service-worker.js`、`src/background/routing.js`、UI 快照消费处。

- 恢复 Pause 时保存检查点、释放锁、取消观察器和等待的顺序。
- 恢复 Stop 时清理会话并返回 `idle` 的终态。
- 恢复 `running`、`scheduled-rest`、`refreshing` 三种持久化状态的恢复逻辑。
- 恢复 SPA 页面变化所触发的停止/清理语义，并验证没有残留锁、观察器、计时器或 Promise。

验收：每一种状态下触发 Pause、Stop、刷新、导航、恢复；锁、存储、UI 快照与旧版行为一致。

### 阶段 6：双基线回归与小批量人工验证

- 单元测试将旧版行为写成断言，不以当前实现的既有断言替代旧版基线。
- 对所有关键场景记录旧版和当前版的事件序列：目标校验、展开、候选、菜单、确认、验证、统计、分页和最终状态。
- 在测试账号、Preview 和小批量真实删除条件下人工验证。生产账号、批量删除和挑战/验证页面不作为首次验收范围。

验收：第 7 节矩阵全部通过；真实页面结果仅记录为有限场景的人工证据，不外推为普适证明。

## 8. 实施与交付纪律

1. 每次恢复前先运行 `git status --short --branch`；已有的用户改动必须保留。
2. 每次只恢复一个可回滚边界，并在提交说明中列明对应的差异编号（例如 D04、D06）。
3. 受影响的 JavaScript 必须运行 `node --check`，随后运行 `npm test` 和 `git diff --check`。
4. 对需要真实页面的步骤，先执行 Preview，再用测试账号和小批量验证；发生挑战、限流、歧义或验证失败时立即暂停。
5. 每个恢复提交都要记录：旧版证据、当前变更文件、自动化测试、人工验证范围、已知未验证项。
6. 未经明确要求不得打包、发布、扩大 `host_permissions`、调用 Instagram 私有接口或修改旧版目录。

## 9. 回滚策略

- 每个阶段独立提交，出现行为不一致时只回滚当前阶段，不回滚用户已有工作。
- 保留阶段开始前的事件序列测试和快照，用于定位第一处时序偏差。
- 如果插件化边界无法无损承载旧版行为，优先在当前 Instagram 插件增加兼容适配层；不得反向修改旧版，也不得以删除旧版分支作为解决方案。
- 只有全部高优先级验收场景通过，且代码审阅确认未扩张行为，才进入下一阶段或交付。

## 10. 当前结论

现有代码与旧版流程并非完全一致，差异主要集中在目标 URL、回复展开顺序、菜单操作前置动作、删除后的稳定确认、连续限额处理、分页结束、状态终态与续跑恢复，以及设置输入语义。

后续恢复必须以本方案第 3 节的旧版时序和第 4 节的逐项决策为验收标准；在完成恢复与测试前，当前实现不应被描述为与旧版删除流程等价。
